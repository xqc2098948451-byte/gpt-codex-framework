# GPT–Codex Framework v1.5.1 Project Adaptation Model Design

## Status

Approved for implementation on 2026-09-11.

## Problem

The universal framework contains safe defaults, but without an explicit adaptation rule GPT can treat those defaults as fixed settings for every project. That makes a project-agnostic governance framework unnecessarily rigid and can produce inappropriate Git, parallelism, verification, review, task, handoff, or discovery settings.

## Design

Configuration is split into three layers:

1. `FRAMEWORK_INVARIANTS` — non-overridable safety and governance boundaries. Projects may only strengthen them.
2. `FRAMEWORK_DEFAULTS` — safe recommended starting values.
3. `PROJECT_PARAMETERS` — project-specific selections recorded in approved `PROJECT.md`.

GPT must assess project scale, risk, stack, repository shape, dependencies, and workflow before selecting material project parameters. It must not mechanically copy defaults. It may intentionally retain a default or choose another value within invariant bounds; material overrides receive a concise rationale.

The normal parallel hard ceiling remains three simultaneous implementation workers. `GIT_WORKTREE` isolation for simultaneous writable workers remains invariant. Bootstrap authorization, Git safety, exact review binding, user approval authority, reconciliation gates, Action Routing, and Handoff Manifest behavior remain invariant.

## Artifact Changes

- `FRAMEWORK.md`: define the three-layer adaptation model and bootstrap obligation.
- `BOOTSTRAP_PROMPT.md`: force GPT to assess/adapt project parameters.
- `PROJECT.template.md`: add the project parameter profile.
- `AGENTS.md`: require Codex to obey approved project parameters without weakening invariants.
- `README.md`: document how universal defaults become project configuration.
- `CHANGELOG.md`: record v1.5.1.
- Current templates: update framework version metadata to 1.5.1 while preserving historical v1.5 documents unchanged.

## Non-goals

- No change to Controlled Parallel Development mechanics.
- No change to Controlled Git permissions.
- No business-project migration.
- No removal or rewrite of framework development history.
