# GPT–Codex Framework v1.6 — Ephemeral Observability & Runtime Verification Design

## Problem

Tests and static checks do not prove runtime behavior such as startup latency, request latency, error rate, or critical-journey span duration. Codex needs temporary observability access per isolated worktree without turning ephemeral telemetry into a second durable source of truth or granting production-monitoring authority.

## Decision

Add an optional, project-parameterized **Ephemeral Observability Protocol**. Runtime telemetry is scoped to the active task/worktree/run, queried by Codex, and deleted with the ephemeral execution environment. Only concise verification summaries and query definitions needed for audit are persisted under `.gpt-codex/observability/`.

## Invariants

- Observability access is task-scoped, environment-scoped, and least-privilege.
- Writable parallel workers must have isolated telemetry namespaces in addition to isolated Git worktrees.
- Raw logs, metrics, and traces from the temporary stack are ephemeral by default.
- Durable evidence records what was checked, the bound implementation identity, the query/assertion, the observed summary, and PASS/FAIL; it does not retain bulk raw telemetry by default.
- Production/external persistent telemetry is not authorized by this protocol and requires separate explicit authorization.
- Runtime verification cannot redefine task acceptance criteria after implementation; thresholds must come from approved project/task requirements or an approved change.

## Defaults and project parameters

Framework defaults:

- `Observability Mode: EPHEMERAL`
- `Observability Verification Policy: REQUIRED_FOR_RUNTIME_TASKS`
- `Logs Query Interface: LogQL` when a compatible log backend is selected
- `Metrics Query Interface: PromQL` when a compatible metrics backend is selected
- `Trace Query Interface: PROJECT_SPECIFIC`
- `Telemetry Isolation: WORKTREE_SCOPED`
- `Raw Telemetry Persistence: EPHEMERAL`
- `Verification Summary Persistence: DURABLE`

Projects may disable observability when runtime instrumentation is unavailable or irrelevant, select different compatible backends/query interfaces, and define task-specific runtime acceptance criteria. Projects may not weaken the isolation, least-privilege, or production-access invariants.

## Lifecycle

For runtime-relevant tasks:

`IMPLEMENTATION -> STATIC/TEST VERIFICATION -> RUNTIME_OBSERVABILITY_VERIFICATION -> IMPLEMENTATION SHA -> FRESH REVIEW`

Parallel units may run isolated telemetry stacks in their own worktrees. Parent-task composition must perform the parent runtime verification required by the task before establishing the semantic Implementation SHA.

## Durable artifact

Use `.gpt-codex/observability/OBS-<TASK>-<NNN>.md` from `OBSERVABILITY_RESULT.template.md` to record a concise durable verification summary. Raw telemetry remains ephemeral unless a project explicitly approves a different retention policy.

## Handoff

Compact Handoff includes only runtime PASS/FAIL, material observed values versus thresholds, anomalies/blockers, and the durable observability artifact reference. Full logs, metric series, and traces are omitted by default.
