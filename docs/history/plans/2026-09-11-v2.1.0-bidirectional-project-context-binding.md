# Bidirectional Project Context Binding Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade the Framework from v2.0.3 to v2.1.0 with one shared, fail-closed project-context binding contract protecting both GPT→Codex instructions and Codex→GPT returns.

**Architecture:** Keep the existing Kernel, Result Envelope, Handoff, Bootstrap, project templates, Validator, and release pipeline. Add a pure shared context decision module, a GPT→Codex Instruction Envelope/schema/renderer, additive identity fields to the existing Result Envelope/Return, and one Built-in Guardrail that composes the shared decision module in both directions. Store the current management project's concrete identity only in its durable management configuration and exclude that file from generic release output.

**Tech Stack:** Python 3, JSON contracts, Markdown governance documents, `unittest`, deterministic ZIP packaging, SHA-256.

**Spec:** `docs/superpowers/specs/2026-09-11-v2.1.0-bidirectional-project-context-binding-design.md`

## Global Constraints

- Project is authoritative; Framework is advisory.
- Identity validation precedes instruction/result interpretation, freshness, permission, authority, and `NEXT_GPT_ACTION`.
- `KERNEL_VERSION` remains `2.0.0`; compare Kernel byte-for-byte with the trusted v2.0.3 release before publishing.
- Keep `SCHEMA_VERSION=1` unless a demonstrated breaking change makes that impossible; do not weaken the security contract to preserve a version.
- Use one shared identity decision core for GPT→Codex and Codex→GPT; do not add a second Handoff or state system.
- Stable identity is an opaque UUID stored in authoritative project `CONTROL.json`; it is not derived from path, name, chat, or model inference.
- `cross-project-context-binding` is a `REQUIRED_SAFETY_GUARDRAIL` after v2.1.0 identity migration; ordinary unrelated Built-ins remain optional.
- Legacy bootstrap binds `bootstrap_target_project_id` to local durable `CONTROL.project_id`; truly uninitialized bootstrap is a narrow hard stop and cannot continue into business work.
- The single machine fact for required Guardrail adoption is the existing `CONTROL.extensions.guardrails[]` item with matching `id`, released `version`, `source: builtin`, and `enabled: true`; no duplicate Guardrail lists are allowed.
- Truly uninitialized bootstrap uses a two-step local challenge: read-only challenge generation first, exact challenge-bound identity creation second, then hard stop.
- The management project's concrete identity must not appear in Built-ins, Kernel, generic templates, or released Framework packages.
- Existing v2.0.3 tests and historical docs/records remain intact.
- No capability-gap analysis, parallel redesign, observability redesign, Git lifecycle redesign, approval redesign, or Harvest redesign.
- Current workspace is not a Git repository; do not invent commits, branches, or HEAD values. Use file-level verification and report the limitation.
