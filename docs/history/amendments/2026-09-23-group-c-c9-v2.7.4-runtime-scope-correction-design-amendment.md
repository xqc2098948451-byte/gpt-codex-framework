## 4. Bounded corrective-replacement rule

A corrective replacement is permitted only when every condition is independently established. Failure is `RECONCILIATION_REQUIRED` or `AMENDMENT_REQUIRED`; the rule is never a generic Work Unit factory.

1. An accepted runtime result explicitly states `AMENDMENT_REQUIRED`.
2. Current production-owner tests or validators prove the omitted scope.
3. No unauthorized remote mutation occurred.
4. Prior candidates, Work Units, instructions, bootstrap refs, and reviews remain immutable evidence.
5. The replacement has a new Work Unit id/path, bootstrap id, and create-only bootstrap ref.
6. It is created one time by `USER_LOCAL` after exact acceptance, never silently rematerialized.
7. Independent PRE review, GPT adjudication, exact USER acceptance, and required remote-verification/termination gates occur before lifecycle advancement.
8. It explicitly supersedes the prior instance only for the corrected final-release purpose while preserving history.
9. It binds an accepted correction Design, applicable accepted Plans, State revision, supersession facts, exact scope, and a fresh authority base.
10. It applies only to this demonstrated runtime amendment and creates no reusable issuance, replacement, or exception subsystem.
