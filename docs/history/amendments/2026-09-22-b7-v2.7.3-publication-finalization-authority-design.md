# B7 v2.7.3 Publication Finalization Authority Design

## 1. Status, trigger, and classification

This is a Design-only candidate that closes the already-observed missing
State/Evidence finalization authority for the v2.7.3 publication. The v2.7.3
publication has already been independently remotely verified. `W`, the
annotated tag, GitHub Release, asset digest and size, `VERSION`, release
record, and `S` ancestry are closed. The current classification is
`PUBLISHED`, not `REMOTE_ACTIVE`; State revision remains `16`.

Phase O requires a separate State/Evidence finalization. No valid current
Work Unit owns the required three finalization paths. The root cause is
`POST_PUBLICATION_NATIVE_FINALIZATION_WORK_UNIT_MISSING`.

This candidate authorizes nothing. It neither alters publication nor makes a
Work Unit, bootstrap, State, Evidence, Plan, or implementation authority
durable.

## 2. Correction architecture and preserved boundaries

The correction reuses the historical v2.7.2+fix.2 three-path finalization
pattern semantically: independently observe the already-published remote
facts, record durable evidence and result facts, then synchronize State only
through a narrowly authorized finalization lifecycle. It creates no new State
system, Evidence system, Result schema, publication mechanism, role, action
vocabulary, generic Work Unit factory, generic bootstrap mechanism, or
Framework module.

The historical finalization artifacts are precedent only, never reusable
authority. Their Work Unit is revision- and version-bound and immutable. This
Design must not reuse any historical bootstrap, seed, Work Unit, or authority.

This Design candidate does not modify `W`, `v2.7.3`, GitHub Release,
publication asset, State, Evidence, any current Work Unit, any bootstrap ref,
Group C implementation, Plugin, or scripts, tests, or schemas. Other than the
three future finalization paths defined here, those remain unavailable unless
separately and validly authorized.

## 6. Native finalization lifecycle and role separation

Only after exact finalization Work Unit integration, the required lifecycle is:

```text
fresh State revision 16
-> native EXECUTION_INSTRUCTION
-> independent PRE_EXECUTION review
-> CODEX_IMPLEMENTER mutates only the exact three paths
-> validators
-> independent POST_EXECUTION review
-> GPT adjudication
-> exact USER finalization-candidate acceptance
-> close CODEX_IMPLEMENTER execution window
-> bounded USER_LOCAL commit/push/main integration
-> independent remote verification
-> State revision 17 becomes durable
```

`CODEX_IMPLEMENTER` must never receive `COMMIT` or `PUSH` authority. One
future exact USER finalization-candidate response may combine
`USER_LOCAL_FINALIZATION_COMMIT_AUTHORIZATION=APPROVE`,
`USER_LOCAL_FINALIZATION_CANDIDATE_PUSH_AUTHORIZATION=APPROVE`, and
`USER_LOCAL_FINALIZATION_MAIN_FAST_FORWARD_AUTHORIZATION=APPROVE_IF_REMOTE_VERIFICATION_PASSES`.
That is `USER_LOCAL` transport authority, not a Work Unit action expansion.

## 7. Exact three-path finalization semantics

`.gpt-codex/evidence/V2.7.3-REMOTE-PUBLICATION-VERIFICATION.json` must record
only independently observed remote v2.7.3 publication facts and bind them to
exact `W`.

`.gpt-codex/evidence/results/RESULT-V2.7.3-PUBLICATION.json` must use the
existing Result/publication contracts and establish only verified facts,
including `status = PASS`, `remote_verification = VERIFIED`, and
`publication_authority = CONFIRMED_PUBLICATION`, with the exact durable
evidence ref. No schema field may be added unless current schema/contracts
already support it.

State finalization must transition revision `16 -> 17`, preserve unrelated
State fields unless an existing validator requires an already-defined
transition, and append the two v2.7.3 Evidence/Result refs. It must set
`continuity.current_remote_ref = refs/heads/main`,
`continuity.latest_verified_remote_sha = fdcda12c6b0b94ac919d507ba8172ccce2f2dea2`,
`continuity.latest_synced_state_revision = 17`,
`continuity.last_verified_result_ref = .gpt-codex/evidence/results/RESULT-V2.7.3-PUBLICATION.json`,
and `continuity.sync_status = SYNCED`.

The next durable action must be a read-only Group C/C0 fresh re-observation
gate, not Group C implementation authority. The later Plan must derive the
exact valid current State field spelling from current schema, validators, and
State conventions; it must not invent an incompatible field.

## 8. `REMOTE_ACTIVE` boundary

Before finalization main integration, v2.7.3 remains `PUBLISHED`. Only after
the exact three-path finalization is independently remotely verified may it
become `REMOTE_ACTIVE`. Only then may C0 begin, and C0 is limited to read-only
fresh capability/current-interface remapping.

This Design does not authorize C1+, v2.7.4 implementation, Plugin, or any
automatic evolution.
