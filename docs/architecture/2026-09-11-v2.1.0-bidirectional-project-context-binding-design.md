# GPT–Codex Framework v2.1.0 — Bidirectional Project Context Binding

## Status and scope

This design defines the single v2.1.0 feature: bidirectional project context
binding. It protects both executable GPT-to-Codex instructions and
Codex-to-GPT result packets from cross-project misrouting while preserving the
v2.0.3 Result Envelope, Paste-ready GPT Return, fixed Framework Source Folder,
release archive, and historical records.

The feature is a governance interface enhancement. It does not add a service,
database, registry, daemon, package manager, second handoff subsystem, second
state machine, or project-specific business policy.

## Invariants

- Project is authoritative; Framework is advisory.
- Identity validation happens before instruction or result interpretation.
- Identity validation happens before `NEXT_GPT_ACTION`, owner approval, state,
  work-unit, Git, architecture, or business-lifecycle authority is considered.
- Machine evidence precedes model inference.
- An identity match proves only project identity; it does not grant execution
  permission.
- A stable identity is independent of project path, folder name, chat title,
  and framework release version.
- Foreign input is untrusted for current-project authority until identity is
  proven; this is a trust boundary, not a claim that the input is malicious.
- There is one shared identity decision core for both communication directions.
- For a v2.1.0 governed project, Project Context Binding is not an optional
  convenience feature. Once identity migration is complete, no executable
  GPT→Codex instruction and no authoritative Codex→GPT result may bypass
  identity validation.
- `cross-project-context-binding` is a `REQUIRED_SAFETY_GUARDRAIL` for every
  governed project that adopts the v2.1.0 Project Context Binding Contract.
  A migrated project cannot disable or omit it while still executing normal
  instructions or processing authoritative returns. Other unrelated Built-ins
  remain optional: `Preinstalled does not mean enabled` still applies to them.
- Existing Kernel Contract remains unchanged: `KERNEL_VERSION = 2.0.0`.
- The Result Envelope schema remains generation `1`: all additions are
  additive/conditional and preserve existing v2.0.3 fields and semantics.
- No executable instruction may mutate an unverified target project.
- For a truly uninitialized project, the first bootstrap interaction is
  read-only and produces only a local bootstrap challenge. Identity creation
  requires a second instruction bound to that exact challenge. After identity
  creation, bootstrap hard-stops and ordinary execution requires a new
  instruction bound to `PROJECT_CONTEXT_ID`.

## Durable project identity

### Authoritative storage

Each governed project stores one stable opaque `project_context_id` in its
authoritative `CONTROL.json`. The existing `project_id` remains for v2.0.x
compatibility and namespace use; it is not silently reinterpreted as the new
context identity.

The project template contains a non-identity placeholder such as
`GENERATE_DURING_BOOTSTRAP`; it never contains a real consumer ID. Bootstrap or
explicit migration generates a UUID once, writes it to the project CONTROL,
and verifies the persisted value. Repeated bootstrap, folder moves, folder
renames, and Framework upgrades reuse the persisted value.

### Required Guardrail machine adoption

The existing `CONTROL.json.extensions.guardrails[]` collection is the single
machine fact for Guardrail adoption; no parallel `enabled_guardrails`,
`selected_guardrails`, or `active_guardrails` list is introduced. A migrated
v2.1.0 project is valid only when this existing collection contains exactly one
valid Built-in item with `id: "cross-project-context-binding"`,
`source: "builtin"`, the released Guardrail `version`, and `enabled: true`.
The item may also carry the existing snapshot/adoption metadata. This is the
`REQUIRED_GUARDRAIL_CONTROL_FIELD` and is read by bootstrap, migration,
Validator, and runtime validation alike.

The Validator distinguishes the field as follows:

- `PRESENT`: exactly one valid matching item exists and `enabled` is true.
- `ABSENT`: no matching item exists.
- `DISABLED`: the matching item exists but `enabled` is false.
- `MALFORMED`: the matching item is duplicated, has invalid/missing identity,
  source/version, or a non-boolean `enabled` value.

Bootstrap and migration write only this existing `extensions.guardrails[]`
item when adopting the v2.1.0 contract. Runtime instruction/result checks read
the same item. Ordinary optional Built-ins continue to use the existing
selection semantics and remain unaffected by this safety exception.

### Bootstrap binding modes

`PROJECT_CONTEXT_BOOTSTRAP` is not an identity-free bypass. For a legacy
governed project that already has durable `CONTROL.project_id` (or an
equivalent durable project identifier), the instruction must carry the
`BOOTSTRAP_TARGET_PROJECT_ID` contract field, represented in the machine
envelope as `bootstrap_target_project_id`. Codex reads the local durable project ID and
compares it before creating the new context ID. A mismatch returns
`CROSS_PROJECT_BOOTSTRAP_MISMATCH`, performs no mutation, and never uses the
project name as authority.

For a truly uninitialized project with no durable project ID or CONTROL,
`UNBOUND_INITIAL_BOOTSTRAP` is a two-step challenge rather than an identity-free
mutation path.

In Step 1, `LOCAL_BOOTSTRAP_CHALLENGE`, Codex performs read-only discovery only,
creates no CONTROL, creates no `PROJECT_CONTEXT_ID`, and changes no file. It
generates a random opaque `BOOTSTRAP_CHALLENGE_ID` and returns
`BOOTSTRAP_CHALLENGE_REQUIRED` with optional `PROJECT_NAME_HINT`,
`REPO_ROOT_HINT`, and `REPOSITORY_FINGERPRINT_HINT`. Those hints are one-time
provenance only and never become the durable identity.

In Step 2, `CHALLENGE_BOUND_BOOTSTRAP`, GPT sends a new
`PROJECT_CONTEXT_BOOTSTRAP` instruction carrying `bootstrap_challenge_id`.
Codex compares it to the locally pending challenge. Only an exact match may
create the minimum authoritative CONTROL, create and verify the stable context
ID, and consume/invalidate the challenge. A mismatch returns
`BOOTSTRAP_CHALLENGE_MISMATCH` with no mutation; a consumed or stale challenge
is rejected. Successful challenge-bound bootstrap hard-stops after identity
creation. GPT must generate a new normally bound instruction for any subsequent
work. Neither step may modify business code, execute a normal Work Unit,
perform destructive Git actions, install Built-ins in bulk, transfer Owner
authority, transition ordinary state, or execute a `NEXT_GPT_ACTION` beyond
identity establishment.

The pending challenge is stored as minimal local bootstrap evidence in the
existing project evidence area; it is not a server, database, daemon, registry,
or second long-term state system.

The Framework Management project also has a durable `.gpt-codex/CONTROL.json`
with its own generated identity and an explicit management-only marker. The
concrete value is local project configuration, not a Built-in, Kernel,
template, or consumer binding. Release packaging excludes this management-only
configuration so a released Framework cannot clone the management project's
identity into another project.

### Identity format and provenance

`project_context_id` is a canonical UUID string and is machine-comparable.
`project_name` is human-readable diagnostic context. A repository path may be
carried only as `*_REPO_ROOT_HINT` provenance; it is never an identity
authority. A repo fingerprint, if later supplied by a caller, is diagnostic
provenance only and cannot invalidate a stable ID after a move.

## Shared Context Binding Contract

The shared machine contract is represented by the following fields:

| Meaning | Machine field | Direction/role |
| --- | --- | --- |
| Stable project identity | `project_context_id` | authoritative CONTROL |
| Human project label | `project_name` | authoritative CONTROL |
| Release compatibility | `framework_version` | instruction/result snapshot |
| Work scope | `work_unit_id` / `target_work_unit` | existing envelope or instruction |
| State freshness | `state_revision` / `expected_state_revision` | result or instruction |
| GPT→Codex target | `target_project_context_id` | instruction envelope |
| Codex local project | `local_project_context_id` | validator input, never guessed |
| Codex→GPT source | `source_project_context_id` | result envelope/return |
| GPT active project | `active_project_context_id` | receiving GPT context |

No `RETURN_TARGET_PROJECT_CONTEXT_ID` is added because the receiving GPT's
active context is the authority and repeating it would create another copy of
the same fact.

## GPT→Codex Instruction Envelope

The framework adds one machine contract and one renderer for a complete,
single-copy instruction block. A normal instruction has at least:

```json
{
  "instruction_id": "<uuid>",
  "instruction_type": "WORK_UNIT",
  "target_project_context_id": "<uuid>",
  "target_project_name": "<diagnostic name>",
  "expected_state_revision": 18,
  "framework_version": "2.1.0"
}
```

`target_work_unit`, `expected_base_sha`, and `permission_scope` are optional
only when they carry real evidence or execution scope. An instruction ID is
unique packet provenance, not project identity.

The text renderer emits the minimal envelope first, then the existing routing
header and task body in one copyable block. It fills generated envelope fields
from the machine input; users do not hand-complete identity, instruction ID,
or revision fields. `PROJECT_CONTEXT_BOOTSTRAP` is the only special type that
may omit a target ID, and only its first uninitialized challenge step may omit
both target identity and challenge identity. The challenge-bound second step
must carry `bootstrap_challenge_id`; the legacy path must carry
`bootstrap_target_project_id`.

## Shared Guardrail decision order

`cross-project-context-binding` is a general Built-in with the classification
`REQUIRED_SAFETY_GUARDRAIL`. It calls one shared pure decision module for both
directions and returns a structured decision with `decision`, `reason`,
identity/freshness status, authority, and mutation/execution flags. The
classification is mandatory only after a project adopts/migrates to the v2.1.0
contract; unrelated Built-ins do not become mandatory.

GPT→Codex decision order:

```text
READ INSTRUCTION ENVELOPE
→ BOOTSTRAP BINDING CHECK if bootstrap (legacy ID or challenge)
→ READ DURABLE LOCAL PROJECT IDENTITY
→ IDENTITY VALIDATION
→ FRESHNESS VALIDATION
→ PERMISSION VALIDATION
→ AUTHORITY VALIDATION
→ EXECUTION
```

Codex→GPT decision order:

```text
READ RESULT IDENTITY FIELDS
→ READ ACTIVE PROJECT CONTEXT
→ IDENTITY VALIDATION
→ FRESHNESS VALIDATION
→ EVIDENCE VALIDATION
→ AUTHORITY VALIDATION
→ NEXT_GPT_ACTION
```

If any identity step fails, later steps do not run.

The shared decision values are:

- `ALLOW`: identity matches and freshness checks pass; permission and
  authority are still evaluated by the existing execution path.
- `DENY`: malformed/missing/mismatched identity or an otherwise prohibited
  foreign packet; current-project mutation is denied.
- `ANALYSIS_ONLY`: an explicit user override permits reading a foreign packet,
  but current-project authority remains `NONE` and no action can execute.
- `BOOTSTRAP_REQUIRED`: the local project has no durable identity, or a
  bootstrap-only instruction is required.
- `RECONCILIATION_REQUIRED`: identity matches but the state revision is stale.

For GPT→Codex, a normal missing target is `DENY` with
`TARGET_PROJECT_CONTEXT_MISSING`; a missing local identity is
`BOOTSTRAP_REQUIRED`/migration-required and cannot be guessed. A legacy
bootstrap must first match `bootstrap_target_project_id` to the local durable
project ID. A truly uninitialized first bootstrap returns
`BOOTSTRAP_CHALLENGE_REQUIRED` without mutation; only a second instruction
with the exact pending `bootstrap_challenge_id` may create identity. A mismatch
is `DENY` with `CROSS_PROJECT_INSTRUCTION_MISMATCH`,
`CROSS_PROJECT_BOOTSTRAP_MISMATCH`, or `BOOTSTRAP_CHALLENGE_MISMATCH` as
applicable and `PROJECT_MUTATION_PERFORMED: NO`. Same names never override
different IDs. Same IDs survive path changes and framework-version differences;
those differences are handled later by compatibility/freshness logic.

For Codex→GPT, a missing active identity is `DENY` with
`ACTIVE_PROJECT_CONTEXT_UNBOUND`; a missing source identity is `DENY` with
`SOURCE_PROJECT_CONTEXT_MISSING`; a mismatch is `DENY` with
`CROSS_PROJECT_CONTEXT_MISMATCH` and `PACKET_STATUS: QUARANTINED`. In every
case, `NEXT_GPT_ACTION` remains non-executable until identity validation
passes.

## Foreign analysis and contamination recovery

An explicit analysis-only request can inspect a foreign instruction or result,
but the decision records `ANALYSIS_ONLY`, `INSTRUCTION_AUTHORITY_FOR_CURRENT_PROJECT:
NONE` or `PACKET_AUTHORITY_FOR_CURRENT_PROJECT: NONE`, and denies mutation,
state transition, owner authority transfer, work-unit transfer, Git mutation,
and action execution.

If foreign input has already influenced reasoning, the framework records
`CONTEXT_CONTAMINATION_DETECTED`, quarantines the foreign packet and derived
decisions as `NON_AUTHORITATIVE`, and returns to the latest valid context
derived from existing CONTROL, STATE revision, Work Unit, Evidence, and
Handoff provenance. Chat-only contamination requires logical recovery only.
Possible repository mutation requires a read-only contamination audit first;
it never triggers automatic `git reset`, `git clean`, `git restore`, or broad
file replacement. A confirmed clean baseline permits return to the trusted
project context.

## Required Guardrail enforcement

After a project completes v2.1.0 identity migration, project validation must
fail if the existing `CONTROL.extensions.guardrails[]` field is absent,
disabled, or malformed for the required Guardrail. An executable instruction
or authoritative return for such a project is `BLOCKED` even when the packet's
identity happens to match, because the required validation path is not active.
The decision must name the missing/disabled guardrail and must not fall back to
project name, path, model inference, or an optional Built-in selection.

Before migration, compatibility evaluation may report
`PROJECT_CONTEXT_ID_MISSING` and a migration result. The project must not be
treated as a fully governed v2.1.0 project until both durable identity and the
required Guardrail are present.

## Bootstrap, migration, and compatibility

New bootstrap creates or confirms the identity, writes authoritative CONTROL,
verifies it, records the required Guardrail in the existing
`CONTROL.extensions.guardrails[]` field, establishes the GPT active context,
and makes future packets carry the ID.
Old projects without the field are detected as
`PROJECT_CONTEXT_ID_MISSING` and receive the existing compatibility result
appropriate to the project, normally `RECOMMENDED_UPGRADE` or
`REQUIRED_MIGRATION`; the implementation must not hard-code one classification
without checking the existing contract. Migration is explicit and idempotent.

Framework upgrades evaluate compatibility but never regenerate or overwrite a
project identity. `Preinstalled does not mean enabled` remains true for
ordinary optional Built-ins. The required safety Guardrail is the explicit
exception once the project adopts/migrates to the v2.1.0 contract; its presence
and enabled enforcement are mandatory for normal execution and authoritative
return processing.

## Result Envelope and Paste-ready Return

The existing Result Envelope remains the only structured source and the GPT
Return remains its derived view. When `return_to_gpt_required` is true, the
Envelope includes `source_project_context_id`, `source_project_name`, and
`framework_version` in addition to its existing work-unit and revision fields.
The renderer emits:

```text
RESULT
SOURCE_PROJECT_CONTEXT_ID
SOURCE_PROJECT_NAME
FRAMEWORK_VERSION
WORK_UNIT
STATE_REVISION
EXECUTION
CHANGED
VERIFY
EVIDENCE
DEVIATIONS
BLOCKERS
NEXT_GPT_ACTION
```

Optional v2.0.3 evidence sections remain unchanged and empty values still
render as `NONE`. Schema generation stays `1` because this is an additive
extension with conditional identity requirements for return packets, not a
reinterpretation of existing required fields. The validator and tests enforce
machine/text identity consistency.

## Validation and release boundary

Framework validation checks the Built-in manifest, catalog, required-safety
classification/enforcement contract, templates,
Instruction Envelope schema, Result Envelope identity fields, bootstrap and
migration documentation, management-identity non-leakage, and the absence of
hard-coded consumer IDs/paths in generic Framework files. The release script
continues to exclude transient files, old archives, and the management-only
identity configuration at the actual path `.gpt-codex/CONTROL.json`, while
including the generic consumer template at
`.gpt-codex/project-template/CONTROL.template.json`.

The release validator and packaging tests must prove that a local management
CONTROL exists, its concrete ID is absent from the ZIP, manifest, Kernel,
Built-ins, generic docs, schemas, and templates, and the generic CONTROL
template remains present with only a non-identity placeholder.

The v2.1.0 release must compare `.gpt-codex/KERNEL.md` byte-for-byte with the
trusted v2.0.3 baseline. Any change is a release blocker. The release contains
only current v2.1.0 artifacts and lightweight metadata; historical ZIPs are
not embedded.

## Explicit non-goals

This version does not implement governance capability-gap analysis, parallel
development redesign, observability redesign, Git lifecycle redesign,
approval-system redesign, Harvest redesign, a network identity service, or a
new state machine.
