# GPT–Codex Framework v2.0.3 — Paste-ready GPT Return and Fixed Framework Source Design

## Status

Approved for implementation on 2026-09-11.

## Goal

Make every required Codex-to-GPT handoff a complete, copyable plain-text result derived from the machine Result Envelope, and document a stable unversioned Framework Source Folder model for consumer workspaces.

## Invariants and scope

- Framework Release Version becomes `2.0.3`.
- Kernel Version remains `2.0.0`.
- Schema Version remains `1`.
- The Kernel Contract is unchanged. `.gpt-codex/KERNEL.md` and `.gpt-codex/scripts/kernel_rules.py` are byte-for-byte protected source files.
- Existing machine Result Envelope fields remain valid; the user-facing return is a derived view, never a second source of truth.
- No Plugin Manager, synchronizer, symlink manager, daemon, new Kernel subsystem, or complex dependency mechanism is introduced.
- Existing historical specs/plans and release history are preserved.
- `dist/` contains only the current v2.0.3 release outputs after publication.

## Design

### Result Envelope and GPT Return Text

The machine envelope remains the authoritative structured fact. Its existing required fields (`kernel_version`, `schema_version`, `project_id`, `work_unit_id`, `extension`, `status`, `evidence_refs`, and `completion_gate`) remain required and valid. The schema adds only explicit result/return fields needed to derive a complete copyable handoff, while retaining Schema Version `1` and `additionalProperties: true`.

The derived formatter accepts one envelope mapping and produces plain text only when `return_to_gpt_required` is true. It emits these sections in stable order for every status (`PASS`, `FAIL`, and `BLOCKED`): `RESULT`, `WORK_UNIT`, `STATE_REVISION`, `EXECUTION`, `CHANGED`, `VERIFY`, `EVIDENCE`, `DEVIATIONS`, `BLOCKERS`, and `NEXT_GPT_ACTION`. Empty scalar/list/object values render as `NONE`. Applicable metadata sections include Git Base / Implementation SHA, Parallel Batch / Execution Unit, Observability / Fitness, and Extension Evidence references; absent values are explicit `NONE`.

The formatter reads all displayed facts from the envelope. It may normalize formatting, but it cannot invent a second result state or independently supplied evidence. The return text intentionally omits raw logs, complete diffs, telemetry, debug traces, and intermediate reasoning; those remain reachable through evidence references.

### Handoff integration

The handoff Built-in documents that its compact human view must call the Result Envelope-derived formatter when `Return To GPT Required = YES`. The project template carries representative fields for this behavior. The `result-envelope` schema names the fields and validates their types without changing the existing Kernel/schema compatibility identifiers.

### Consumer Workspace Setup

Consumer documentation standardizes a fixed, unversioned auxiliary Framework Source Folder such as `gpt-codex-framework` or `通用开发框架管理`. The project remains authoritative and the Framework remains advisory. Kernel and Built-ins are read-only during ordinary project work. Built-ins are copied into a project-local versioned snapshot when adopted. A Framework upgrade does not automatically modify a project and must first run the compatibility scan, whose results remain `NO_ACTION`, `OPTIONAL_REUSE`, `RECOMMENDED_UPGRADE`, `REQUIRED_MIGRATION`, or `CONFLICT`.

For a consumer currently bound to a versioned folder, migration is a one-time operation: remove the old versioned auxiliary folder, add the fixed folder, save project configuration, and use that fixed folder for future Framework upgrades.

### Release and history

The root `VERSION`, catalog metadata, current docs, changelog, release record, and release index are updated for v2.0.3. A v2.0.3 spec and plan are added without editing prior history. The existing project-local `framework-release` Skill remains the publication mechanism; only directly relevant minimal changes are allowed.

## Verification contract

The new tests must prove:

1. PASS, FAIL, and BLOCKED each produce complete paste-ready text.
2. Required sections cannot be omitted.
3. Empty fields consistently render `NONE`.
4. Large logs are not required in the return contract.
5. The Result Envelope schema remains valid with Kernel `2.0.0` and Schema `1`.
6. Return Text is derived from the envelope and cannot become an independent fact source.
7. The fixed-folder workspace rules are present and versioned folder binding is rejected by the validator/documentation contract.
8. Kernel Contract files are byte-for-byte unchanged versus the v2.0.2 release package.
9. Framework validation, all tests, release metadata/index consistency, ZIP integrity, and ZIP hygiene pass before publication.
