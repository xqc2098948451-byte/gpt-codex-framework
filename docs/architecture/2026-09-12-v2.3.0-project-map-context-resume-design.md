# GPT–Codex Framework v2.3.0 — Project Map, Context Checkpoint & Delta Resume

## Status

Approved architecture for the next feature release after Framework `2.2.1`.

This document supersedes the earlier local draft named:

`2026-09-12-v2.3.0-context-checkpoint-delta-resume-design.md`

The combined v2.3.0 design has two tightly coupled capabilities:

1. **Project Navigation Map** — answers “where should GPT look?”
2. **Context Checkpoint & Delta Resume** — answers “what does GPT already know, and what changed?”

Together they change the default development/maintenance path from repository-wide rediscovery to:

```text
identity
→ project map
→ candidate modules
→ resume checkpoint
→ relevant Git delta
→ minimum required reads
→ work
→ incrementally refresh affected navigation/resume state
```

## Baseline

Inspected Framework baseline:

- Framework release: `2.2.1`
- Kernel: `2.0.0`
- Schema generation: `1`
- Existing bootstrap uses progressive disclosure.
- Existing resume implementation: `.gpt-codex/scripts/continuity_resume.py`
- Existing repository discovery Built-in: `.gpt-codex/builtins/skills/repository-discovery/`
- Existing project description: `.gpt-codex/PROJECT.md`
- Existing GitHub continuity authority: `STATE.continuity`
- Existing Handoff is derived and non-authoritative.
- Existing Framework Maintenance guidance does not provide a persistent business-project navigation index.

The design is additive. It does not create a second state authority and does not replace `CONTROL.json`, `STATE.json`, Work Units, Evidence, Result Envelopes, source code, tests, Git, or GitHub observations.

---

## 1. Problem

Two forms of repeated work currently waste GPT/Codex context and time.

### 1.1 Context transition waste

When GPT must continue in a new UI/conversation because the context window is exhausted, the next session can reread project-level documents and reconstruct context that was already known.

### 1.2 Maintenance rediscovery waste

When a user later asks to maintain or change an existing project, GPT may inspect directory trees, search broad source areas, reread architecture documents, and rediscover module ownership before it knows where the requested behavior lives.

These are different questions:

```text
Project Map:
“Where is this concern implemented?”

Resume Checkpoint:
“What was already understood, what was being changed, and what changed since?”
```

A complete solution needs both.

---

## 2. Design Objective

For a normal maintenance request, target complexity should approach:

```text
O(project-map lookup
  + candidate module maps
  + changes since relevant anchors
  + active working set)
```

rather than:

```text
O(repository size)
```

The core behavioral rule is:

> GPT should understand where to look before deciding what to read.

---

## 3. Framework Invariants

The following rules are normative for v2.3.0.

> A context-window transition is not a project bootstrap.

> A maintenance request is not a repository rediscovery.

> A maintenance request starts from the Project Map, not from repository-wide discovery.

> Do not scan the repository when the Project Map can identify the candidate module.

> A valid Resume Checkpoint skips unchanged context; it does not replace canonical project state.

> A Project Map is a derived navigation index; it never outranks actual source code, tests, canonical governance records, Git, or GitHub facts.

---

## 4. Authority Model

Authority order remains:

1. actual project source/configuration/test files for implementation facts;
2. `CONTROL.json` for project identity/governance selection;
3. `STATE.json` for governed execution state;
4. active Work Unit / Evidence / Result Envelope;
5. Git/GitHub for observed repository facts and continuity;
6. `PROJECT.md` for explanatory project profile/architecture;
7. `PROJECT_MAP.json` and module maps as **derived navigation indexes**;
8. `RESUME.json` as **derived continuation cache**;
9. Handoff / GPT Return as derived presentation.

Neither navigation nor resume documents may overwrite or reinterpret canonical state.

## 5. Project Navigation Map

### 5.1 Location

```text
.gpt-codex/
└── navigation/
    ├── PROJECT_MAP.json
    └── modules/
        ├── <module-id>.json
        └── ...
```

### 5.2 Why two levels

A single large map would eventually become another document GPT must load in full.

Therefore v2.3.0 uses:

```text
PROJECT_MAP.json
    lightweight global routing index

modules/<module-id>.json
    detailed local navigation for one bounded area
```

GPT normally reads one global map and only the module maps relevant to the user request.

### 5.3 Project Map role

`PROJECT_MAP.json` answers:

- what major modules/areas exist;
- what each module is responsible for;
- which paths belong to the module;
- useful semantic keywords;
- important entry points;
- where its detailed module map lives;
- whether that module map is currently verified/stale/unknown.

It must not attempt to document every source file.

### 5.4 Proposed Project Map shape

```json
{
  "schema_version": 1,
  "authority": "DERIVED_NAVIGATION_INDEX",
  "project_id": "PRJ-...",
  "project_context_id": "uuid",
  "repository_id": null,
  "anchor_sha": "abc123",
  "architecture_summary": "Short routing-oriented summary only.",
  "modules": [
    {
      "id": "auth",
      "purpose": "Authentication, session and token lifecycle.",
      "paths": [
        "src/auth/",
        "tests/auth/"
      ],
      "entry_points": [
        "src/auth/index.ts"
      ],
      "keywords": [
        "login",
        "authentication",
        "session",
        "token",
        "refresh"
      ],
      "module_map": ".gpt-codex/navigation/modules/auth.json",
      "verified_at_sha": "abc123",
      "freshness": "VERIFIED"
    }
  ]
}
```

### 5.5 Module Map role

A module map is a focused navigation document for one module.

It should contain enough information to find likely implementation locations without opening the whole module.

Proposed shape:

```json
{
  "schema_version": 1,
  "authority": "DERIVED_NAVIGATION_INDEX",
  "project_id": "PRJ-...",
  "project_context_id": "uuid",
  "module_id": "auth",
  "responsibility": "Authentication, session and token lifecycle.",
  "tracked_paths": [
    "src/auth/",
    "tests/auth/"
  ],
  "key_files": [
    {
      "path": "src/auth/session.ts",
      "role": "Session lifecycle."
    },
    {
      "path": "src/auth/token.ts",
      "role": "Token issuance and refresh."
    }
  ],
  "interfaces": [
    "POST /login",
    "POST /refresh"
  ],
  "depends_on": [
    "users",
    "database"
  ],
  "tests": [
    "tests/auth/"
  ],
  "configuration": [
    "config/auth.ts"
  ],
  "data_models": [
    "Session",
    "RefreshToken"
  ],
  "read_when": [
    "login failures",
    "session expiry",
    "token refresh",
    "authentication changes"
  ],
  "verified_at_sha": "abc123",
  "freshness": "VERIFIED"
}
```

### 5.6 Map contents should be semantic, not exhaustive

Useful map fields are:

```text
purpose
responsibility
keywords
read_when
entry_points
key_files + roles
tests
interfaces
dependencies
configuration
data models
tracked paths
```

Avoid enumerating every file merely because it exists.

The map is a routing index, not a replacement for source browsing.

## 6. Project Map Routing Modes

Every normal maintenance request should select one navigation mode before broad repository search.

### 6.1 MAP_HIT

Use when the Project Map clearly identifies one or more candidate modules and their maps are sufficiently fresh.

Behavior:

```text
read PROJECT_MAP
→ read matching module map(s)
→ verify candidate files
→ continue with Resume/Delta
```

Repository-wide discovery is forbidden.

### 6.2 MAP_PARTIAL

Use when the map identifies a likely module but lacks enough detail, or the relevant module map is stale.

Behavior:

```text
read PROJECT_MAP
→ read likely module map
→ perform bounded search only inside tracked/candidate paths
→ refresh that module map
→ continue
```

Do not expand to the entire repository unless bounded evidence fails.

### 6.3 MAP_MISS

Use when no module plausibly covers the request or changed paths reveal a new architectural area not represented in the map.

Behavior:

```text
perform scoped discovery
→ identify the missing/new module
→ update PROJECT_MAP
→ create/update module map
→ continue with target reads
```

A miss is not permission for automatic full repository rediscovery. Discovery should expand progressively.

---

## 7. Map Freshness

Routing confidence and freshness are separate concepts.

Allowed freshness values:

```text
VERIFIED
STALE
UNKNOWN
```

### 7.1 VERIFIED

The module's relevant tracked paths have no known changes after its verification anchor.

### 7.2 STALE

Git delta intersects a module's tracked paths after `verified_at_sha`, or a key file referenced by the map is missing/moved/changed in a way that invalidates navigation assumptions.

### 7.3 UNKNOWN

The framework cannot safely determine freshness, for example because required Git history is unavailable.

Unknown does not invalidate the whole project map. It causes bounded verification of the candidate area.

---

## 8. Incremental Map Maintenance

The map must not be regenerated globally after every change.

### 8.1 Initial creation

For a new governed project:

```text
repository-discovery
→ evidence-derived project profile
→ PROJECT.md
→ initial PROJECT_MAP
→ initial module maps
```

Repository Discovery remains the one-time mechanism for learning an unbound/new project.

### 8.2 Existing project without a map

Backward compatibility requires old projects to remain usable.

For a v2.2.1 project adopted into v2.3.0:

```text
valid canonical project
+ no PROJECT_MAP
→ MAP_MISSING
→ one-time map generation on the next suitable maintenance/bootstrap operation
```

Absence of a map is not a project validation failure in v2.3.0.

### 8.3 Normal incremental update

After a successful work unit:

```text
old navigation anchor
→ Git changed paths
→ identify affected modules
→ update only affected module maps
→ update PROJECT_MAP only if routing metadata/module boundaries changed
```

Examples:

```text
src/auth/session.ts changed
→ refresh auth module map only
```

```text
new src/payments/ subtree added
→ MAP_MISS / new module
→ add payments module to PROJECT_MAP
→ create payments module map
```

### 8.4 Durable update boundaries

Maps should be refreshed at durable boundaries, not every edit:

- verified Work Unit completion;
- material file move/rename;
- new module/subsystem introduction;
- module boundary change;
- successful bounded discovery after `MAP_PARTIAL`;
- successful discovery after `MAP_MISS`;
- before a handoff when known navigation facts materially changed.

## 9. Context Checkpoint & Delta Resume

### 9.1 Location

```text
.gpt-codex/
└── continuity/
    └── RESUME.json
```

### 9.2 Role

`RESUME.json` stores already-understood continuation context, not canonical project state.

Proposed structure:

```json
{
  "schema_version": 1,
  "authority": "DERIVED_CACHE",
  "project_id": "PRJ-...",
  "project_context_id": "uuid",
  "repository_id": null,
  "checkpoint": {
    "state_revision": 42,
    "active_work_unit": "WU-...",
    "anchor_sha": "abc123",
    "remote_ref": null,
    "latest_verified_remote_sha": null
  },
  "context_sources": [
    {
      "path": ".gpt-codex/PROJECT.md",
      "fingerprint": "sha256:..."
    },
    {
      "path": ".gpt-codex/navigation/PROJECT_MAP.json",
      "fingerprint": "sha256:..."
    },
    {
      "path": ".gpt-codex/navigation/modules/auth.json",
      "fingerprint": "sha256:..."
    }
  ],
  "current_objective": "Fix refresh-token expiry.",
  "completed": [],
  "open_decisions": [],
  "blockers": [],
  "working_set": {
    "hot_modules": [
      "auth"
    ],
    "hot_files": [
      "src/auth/session.ts"
    ],
    "next_required_reads": [
      "tests/auth/session.test.ts"
    ],
    "invalidated_context": []
  },
  "verification": {
    "last_result_ref": null,
    "evidence_refs": []
  }
}
```

`hot_modules` connects Resume to Project Map routing.

## 10. Resume Modes

### 10.1 FAST_RESUME

Conditions:

- project identity matches;
- repository identity matches when applicable;
- checkpoint schema is valid;
- checkpoint revision matches canonical STATE;
- relevant context fingerprints match;
- active Work Unit identity matches;
- no continuity reconciliation condition exists.

Behavior:

- do not run repository discovery;
- do not reread unchanged `PROJECT.md`;
- do not reread unchanged `PROJECT_MAP`;
- do not reread unchanged active module maps;
- restore objective/decisions/blockers/hot modules/hot files;
- read only `next_required_reads` plus evidence required by current action.

### 10.2 DELTA_RESUME

Use when identity is valid but the repository or canonical state advanced explainably.

Behavior:

1. compute/obtain changed paths since checkpoint anchor;
2. mark only affected cached context invalid;
3. mark only affected module maps stale;
4. read changed governance sources if relevant;
5. read changed hot files;
6. read stale candidate module maps;
7. expand only when evidence requires it;
8. refresh checkpoint at next durable boundary.

### 10.3 COLD_RESUME

No usable checkpoint, but valid governed project exists.

Behavior:

```text
identity
→ Project Map if available
→ canonical progressive disclosure
→ create first checkpoint at next authorized durable boundary
```

Do not select Bootstrap merely because the checkpoint is absent.

### 10.4 RECONCILIATION_REQUIRED

Existing fail-closed semantics remain for:

- identity mismatch;
- repository mismatch;
- conflicting canonical state;
- unreachable/divergent remote facts;
- impossible checkpoint revision;
- conflicting Work Unit/result facts.

Checkpoint and map documents remain diagnostic only.

### 10.5 BOOTSTRAP

Use only when project governance/identity does not exist or is not validly bound.

A new GPT conversation or UI is never sufficient reason to select Bootstrap.

## 11. Unified Maintenance Entry Flow

The default v2.3 maintenance flow becomes:

```text
USER REQUEST
    │
    ▼
Minimal project identity check
    │
    ▼
PROJECT_MAP.json
    │
    ├──────────── MAP_HIT ─────────────┐
    │                                  │
    ├────────── MAP_PARTIAL ──────┐    │
    │                              │    │
    └──────────── MAP_MISS ──┐     │    │
                             ▼     ▼    ▼
                       scoped discovery/module map
                             │
                             ▼
                         RESUME.json
                             │
                             ▼
                      relevant Git delta
                             │
                             ▼
                  minimum required file reads
                             │
                             ▼
                       analyze / modify
                             │
                             ▼
              verification / result / evidence
                             │
                             ▼
               refresh affected module map(s)
                             │
                             ▼
                    refresh RESUME.json
```

## 12. Ordering Between Map and Resume

For a brand-new maintenance request:

```text
identity → map → resume → relevant delta → files
```

For a context-window continuation where the Resume checkpoint already declares `hot_modules`:

```text
identity
→ validate RESUME identity
→ load PROJECT_MAP only if its fingerprint/freshness requires it
→ use hot_modules
→ relevant module maps
→ delta
→ files
```

This preserves the optimization:

- the map prevents repository rediscovery;
- the checkpoint prevents rereading the map when the map itself is unchanged.

---

## 13. Repository Discovery Changes

The existing Repository Discovery Built-in remains read-only.

Its role becomes explicit:

### Allowed

- first-time bootstrap of an unbound project;
- one-time initial Project Map creation evidence;
- `MAP_MISS` scoped discovery;
- `MAP_PARTIAL` bounded discovery within candidate paths;
- explicit user-requested architecture rediscovery.

### Forbidden by default

- running repository-wide discovery for every maintenance request;
- running repository-wide discovery merely because GPT changed UI/context;
- rerunning discovery when a valid map already identifies the candidate module.

Repository Discovery should produce concise evidence suitable for updating navigation assets, but it should not itself become project state authority.

## 15. Runtime Helpers

Prefer focused modules rather than making `continuity_resume.py` own navigation.

### 15.1 New helper

```text
.gpt-codex/scripts/project_navigation.py
```

Responsibilities:

- load navigation documents;
- validate identity binding;
- compute module freshness from changed paths;
- identify affected modules from tracked paths;
- build bounded navigation read plans;
- never claim implementation authority.

Suggested interfaces:

```python
load_project_map(root: Path) -> dict[str, Any] | None

load_module_map(
    root: Path,
    relative_path: str,
) -> dict[str, Any]

validate_navigation_identity(
    navigation: dict[str, Any],
    control: dict[str, Any],
) -> None

affected_modules(
    project_map: dict[str, Any],
    changed_paths: list[str],
) -> list[str]

classify_map_route(
    candidate_module_ids: list[str],
    *,
    stale_module_ids: list[str],
) -> str
```

Natural-language semantic matching remains a GPT responsibility using the compact Project Map; Python does not need an embedding or NLP dependency.

### 15.2 Existing helper

Extend:

```text
.gpt-codex/scripts/continuity_resume.py
```

to understand:

- `RESUME.json`;
- context fingerprints;
- `hot_modules`;
- `hot_files`;
- minimum required reads;
- FAST/DELTA/COLD/RECONCILIATION classification.

## 17. Project Validation

For v2.3.0 backward compatibility:

### Navigation absent

Valid.

The project may return:

```text
MAP_MISSING
```

and create navigation assets at the next authorized suitable boundary.

### Navigation present

Must validate:

- JSON shape/schema version;
- `authority == DERIVED_NAVIGATION_INDEX`;
- project ID binding;
- project context ID binding;
- repository ID binding when supplied;
- unique module IDs;
- valid module-map paths;
- module-map `module_id` matches the owning Project Map entry.

Invalid navigation cannot corrupt canonical state.

### Resume absent

Valid → `COLD_RESUME`.

### Resume present

Must validate identity/cache contract as defined above.

## 20. Kernel Decision

Preferred implementation keeps Kernel `2.0.0` unchanged.

Reason:

- navigation and resume are performance/workflow protocols;
- they are not new execution states;
- they can be implemented at Framework Bootstrap, scripts, schema/templates, and Built-in behavior level.

If implementation discovers that a Kernel invariant must change, Kernel must be explicitly versioned rather than silently edited.

## 22. Required Regression Tests

At minimum:

1. valid Project Map loads without repository discovery;
2. map identity mismatch is rejected;
3. `MAP_HIT` selects candidate module maps only;
4. `MAP_PARTIAL` limits search to candidate module paths;
5. `MAP_MISS` permits scoped discovery and requires map update;
6. changed path inside `auth` marks only `auth` stale;
7. unrelated changed path does not invalidate every module;
8. missing map remains backward-compatible;
9. valid checkpoint → `FAST_RESUME`;
10. unchanged `PROJECT.md` fingerprint is omitted from reads;
11. unchanged Project Map fingerprint is omitted from reads;
12. unchanged module-map fingerprint is omitted from reads;
13. changed hot file → `DELTA_RESUME`;
14. changed module path marks only its module stale;
15. unrelated repository change does not force full context reload;
16. missing checkpoint → `COLD_RESUME`, not Bootstrap;
17. foreign project/repository IDs fail closed;
18. local unsynced checkpoint is not presented as latest synced remote state;
19. Handoff renders map/resume fields but remains non-authoritative;
20. consumer projection includes generic navigation/resume assets but not management-project generated map/cache;
21. prompt regression test forbids unconditional repository discovery for normal maintenance;
22. prompt regression test forbids unconditional project reread on context transition;
23. Kernel remains unchanged unless explicitly versioned.

---

## 23. Success Criteria

The feature is complete when all of the following are true:

- A normal maintenance request reads Project Map before broad repository search.
- GPT can identify likely modules without scanning the full repository.
- A `MAP_HIT` reads only the relevant module map(s) and candidate files.
- Small changes invalidate only affected module maps.
- A context-window continuation does not reread unchanged project/map/module context.
- New GPT UI/conversation never implies project bootstrap.
- Missing navigation/checkpoint remains compatible with v2.2.1 projects.
- Navigation and resume documents remain strictly derived.
- Repository-wide discovery is reserved for bootstrap, explicit rediscovery, or evidence-driven expansion.
- The effective normal cost is approximately `map lookup + relevant delta + working set`, not repository size.

---

## 24. Final v2.3.0 Product Model

v2.3.0 should be described as:

**Project Map + Context Checkpoint + Delta Resume**

with the combined rule:

> Locate first, verify freshness second, read only what is necessary.

And the two anti-regression invariants:

> A context-window transition is not a project bootstrap.

> A maintenance request is not a repository rediscovery.
