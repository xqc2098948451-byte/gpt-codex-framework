## Validation and public gates

The release path is: independent Design/Plan review → GPT adjudication → exact USER acceptance → exact Design/Plan integration → independent remote verification → fresh `origin/main` observation and `PUBLIC_RELEASE_AUTHORITY_BASE_SHA` freeze → Git ancestry check → exact source-object materialization → portal/package preflight → publisher facts → bounded Public Release Work Unit and PRE → package/listing validation → clean install and representative positive/negative use tests → submission materials and portal draft → independent release POST → explicit user approval to **Submit for Review** → portal submission → OpenAI review → separate explicit user approval to **Publish** after approval → portal Publish → independent observation of the public directory listing → publication evidence. No Public Release Work Unit may be created before exact Design/Plan acceptance, integration, independent remote verification, and fresh authority-base observation. Submission draft creation is an external Platform action, and its exact payload and any portal-side normalization must be recorded before the submission approval. A Work Unit that permits submission must not also permit publication as one irreversible action.

`SUBMIT_FOR_REVIEW != PUBLICATION`; `APPROVED != PUBLISHED`; `PUBLISHED != FRAMEWORK_ACTIVATED`. Pending review is `PLUGIN_PUBLIC_RELEASE_STATUS = SUBMITTED_AWAITING_REVIEW`, never PASS. Public-release success requires portal acceptance, OpenAI approval, an explicitly executed Publish action, and an independently observed listing in the Universal Plugins Directory. Publication is an external Platform action; local package tests cannot establish it.

If validation or submission fails, retain the error and draft evidence, correct only within bounded authority, or withdraw/abandon the draft through a separately authorized portal action when available. If approval is denied, stop and route the finding for review. If publication later needs withdrawal, use a new explicit decision and the portal's actual available controls; do not assume automatic rollback or change any Project state.

## Governance economy and exclusions

Reference the already verified exact SHA and fingerprint rather than repeatedly proving them. Embed non-durable PRE objects in dependent tasks or bundle them by an exact immutable payload. Format-only corrections stay within existing authority when scope and semantics are unchanged. These are requirements for this release flow and inputs to Post-P2 Foundation, not Framework code changes here.

Excluded: P2 implementation changes, Framework version change, `STATE` mutation, Framework release, Hooks, Foundation, P3, P4, new MCP under this accepted release design, new state/store/registry, automatic publication, and automatic activation. MCP would require an actual later requirement and a change to the accepted release design. Public release itself never authorizes Framework adoption or Project mutation.
