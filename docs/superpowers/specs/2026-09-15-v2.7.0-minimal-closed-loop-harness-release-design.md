## Purpose and Version Decision

v2.7.0 packages and publishes the accepted, merged Minimal Closed-Loop Harness upgrade; it introduces no further architectural feature set.

The release is additive Framework capability expansion, a backward-compatible transition, no Kernel contract version change, no schema generation change, and no removal of P0 authorities.

The version is `2.6.0 -> 2.7.0` because this is substantive additive Framework capability release without a breaking Kernel/schema reset.

`2.6.1` is too narrow for the architectural capability expansion; `3.0.0` is rejected because no incompatible Kernel/schema reset is introduced.

> Preserve capability, compress structure; preserve the closed loop, remove duplication.

Publication may package accepted capability but may not silently delete or merge existing P0 responsibility.

## Candidate W, Integration, and Tag

`W` means the reviewed release-candidate source commit, created later on a dedicated release branch derived from accepted main.

W contains the v2.7.0 version surface, CHANGELOG entry, version-consistency updates, generated current release record/index, and generated deterministic artifact/sidecars.

W is a source candidate and publication candidate, NOT confirmed publication; before remote verification its authority is `PUBLICATION_CANDIDATE_ONLY`.

W must pass all release and full-suite validations before integration/publication is proposed.

Integration is `release branch -> independent review -> Pull Request -> merge to main`; after merge W must be an ancestor of remote main.

W must not be rewritten, squashed, or rebased if that destroys the immutable source candidate; the later Plan preserves W ancestry.

The annotated `v2.7.0` tag target is W only when W is independently accepted, remotely present, an ancestor of remote main, artifact/hash-verified, and publication is separately authorized.

Tag creation is not authorized in this Design Work Unit.

## Publication and Management Attestation P

Publication is a separate authorization after W acceptance and integration; local artifact generation never implies publication.

Later publication may create the annotated W tag, GitHub Release, and canonical bootstrap ZIP, then verify remote metadata, artifact SHA-256, artifact size, and tag target.

`P` means management-only post-publication attestation created only after remote publication is TOOL_OBSERVED.

P records W SHA, remote main containing W, v2.7.0 tag target, GitHub Release id/url, canonical artifact SHA-256/size, validator/test results, and publication authority.

P references verified remote evidence, never self-authorizes publication, never claims its own SHA before it exists, and is never required by consumer runtime.

P does not self-reference P.

Before remote verification `publication_authority = PUBLICATION_CANDIDATE_ONLY`; only VERIFIED remote verification, SYNCED state, durable verified evidence refs, and remote head/source evidence may establish `CONFIRMED_PUBLICATION`.

Local artifact generation alone cannot establish PASS, SYNCED, or CONFIRMED_PUBLICATION.

## Failure and Recovery

Release-preparation failure means no publication.

If PR integration changes or replaces W unexpectedly, stop and re-adjudicate source/tag target.

If remote tag/release/asset verification fails, publication remains unconfirmed with no CONFIRMED_PUBLICATION and no synced final Result.

If P creation fails after observed remote publication, publication remains a remote fact but attestation is incomplete; recover from remote GitHub facts and never fabricate P.
