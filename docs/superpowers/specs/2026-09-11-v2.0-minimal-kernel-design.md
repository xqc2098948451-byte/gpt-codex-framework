# GPT–Codex Framework v2.0 Minimal Kernel Design

**Status:** APPROVED DESIGN

## Goal

Replace the v1.x monolithic governance template with a small, stable Kernel that governs project adaptation, state, authority, evidence, extensions, reconciliation, and framework compatibility while pushing project-specific behavior into Skills, Guardrails, and Fitness Functions.

## Architecture

v2.0 uses a dual-root workspace. The project root is authoritative and writable. The framework root is auxiliary: Kernel and Built-ins are read-only during ordinary project execution, while the current project may write only to its own Harvest Inbox namespace. Framework upgrades are evaluated by compatibility scan and never propagated automatically.

The Kernel defines contracts, not project technology. A project enables curated Built-ins only when evidence justifies them. Remaining gaps may become project-local extensions only after reuse/configure/compose/degrade options fail. Project-local extensions are exported as normalized Harvest Candidates; repeated cross-project evidence may later promote a candidate to Built-in during framework maintenance.

## Kernel scope

1. Project Adaptation Contract
2. Minimal Work Unit Model
3. Minimal State Machine with optimistic revision
4. Authority / least privilege
5. Evidence model with provenance, freshness, and identity binding
6. Extension Contract for Skill / Guardrail / Fitness
7. Governance compilation and validation
8. Reconciliation
9. Progressive disclosure
10. Governance YAGNI / complexity control
11. Kernel versioning, compatibility, and migration contract

Anything that can safely be absent from some projects does not belong in the Kernel.

## Core principles

- Project is authoritative; Framework is advisory.
- Preinstalled does not mean enabled.
- Reuse before extension.
- Configure before create.
- Compose before create.
- Degrade before extend when the requirement still remains satisfied.
- Evidence before extension.
- Default decision is DO NOT ADD.
- Sufficient governance, not maximal governance.
- Generalize after repetition, not before.
- Framework upgrades are evaluated, not propagated.
- Derived information is not another source of truth.
- Machine-verifiable guarantees should not depend on model memory.

## Dual-root permissions

Ordinary project execution:

- `project/`: read/write according to project authorization.
- `framework/kernel/`: read-only.
- `framework/builtins/`: read-only.
- `framework/harvest/inbox/<current-project-id>/`: candidate write/update permitted.
- other projects' Harvest namespaces: read-only or unavailable.
- Built-in promotion: forbidden outside framework maintenance.

Source projects remain authoritative. Harvest processing never edits source projects. Promotion never silently pushes changes back to source projects.

## Built-ins

v2.0 ships a deliberately small curated catalog. Required Built-ins cover repository discovery, verification/result normalization, derived handoff, framework compatibility evaluation, Harvest export, and universal safety. Basic Git and generic test/build fitness executors are optional. More specialized capabilities remain project-local until repeated evidence justifies promotion.

## Extension maturity

`PROJECT_LOCAL -> HARVEST_CANDIDATE -> SHARED_CANDIDATE -> BUILTIN -> DEPRECATED/RETIRED`

Only `BUILTIN` is reusable as a framework-provided capability. A Harvest Candidate is not a Built-in and cannot be automatically adopted by other projects.

## Governance compile gate

Before development authorization, machine-readable project governance must validate: schema/version, referenced Built-ins/extensions, unique IDs, permission narrowing, state legality, required capability availability, and extension provenance. Governance design remains GPT responsibility; mechanical consistency is Kernel validation responsibility.

## State and evidence

Kernel states are intentionally small: `PROPOSED`, `AUTHORIZED`, `ACTIVE`, `VERIFYING`, `COMPLETE`, plus `BLOCKED`, `AWAITING_APPROVAL`, and `RECONCILIATION_REQUIRED`.

State updates use optimistic revisions. A writer must bind to the expected current revision; stale writes reconcile instead of overwriting newer state.

Evidence sources are distinguished at minimum as `TOOL_OBSERVED`, `USER_ASSERTED`, `SYSTEM_DERIVED`, and `MODEL_INFERRED`. Model inference can guide investigation but cannot independently authorize completion, privilege escalation, destructive action, or other high-impact transitions.

## Upgrade model

Projects record both adopted framework version and last evaluated framework version. A newer framework triggers read-only compatibility evaluation. Results are `NO_ACTION`, `OPTIONAL_REUSE`, `RECOMMENDED_UPGRADE`, `REQUIRED_MIGRATION`, or `CONFLICT`. Evaluation does not imply adoption.

Kernel upgrades never silently reinterpret existing project governance. Incompatible changes require an explicit migration plan and validation.

## Harvest model

Project-local extensions export normalized, provenance-bound candidates into the current project's Harvest Inbox. Export should remove project-private implementation details unless necessary for the semantic contract. Framework maintenance compares semantic identity, intent, triggers, invariants, permissions, outputs, failure semantics, and context. Shared abstractions are extracted from repeated evidence rather than copied from one project.

## Non-goals for v2.0

No marketplace, remote registry, dependency solver, generic DAG scheduler, custom policy language, CI replacement, observability replacement, Git abstraction platform, vector memory system, event-sourcing system, or automatic multi-agent negotiation belongs in the Kernel.
