# GPT–Codex Framework v2.2.0 — GitHub-backed Project Continuity & Coordination

## Status and baseline

This is the frozen design for the proposed `2.2.0` Framework release. It is
design-only: it does not change `VERSION`, Kernel, schemas, Built-ins, release
artifacts, or any consumer project.

The inspected baseline is:

- Framework release: `2.1.0`
- Kernel: `2.0.0`
- Schema generation: `1`
- Management project context: `cb1e0450-df32-4ff6-8a33-35187b69a866`
- Framework Validator: PASS
- Existing test suite: 62 tests, PASS
- Trusted v2.1.0 artifact SHA-256:
  `6fbc03519c6fc84b613d79921606ea3e372bdeb24c60e7a2f9a1bbdadcbf35b1`
- Current Kernel SHA equals the Kernel extracted from that artifact;
  `KERNEL_CONTRACT_CHANGED=NO`

The Framework Management directory is not currently a Git repository. That is
an observed baseline fact, not a reason to initialize one during this design
phase.

## Problem

Chat history is not a durable authority for project state. After a GPT window
changes, GPT must be able to resume from a selected private GitHub repository
without confusing another project, while Codex must be able to continue local
work when GitHub is unavailable without falsely claiming that the work is
formally complete.

The current v2.1.0 contract binds both directions to
`PROJECT_CONTEXT_ID`, but it has no stable repository binding, no remote
freshness contract, no explicit local/remote sync result, and no resume entry
that tells GPT which verified remote state to trust.

## Goals

`GITHUB_MODE = DEFAULT_WITH_LOCAL_DEGRADATION`.

1. Bind one governed project to exactly one GitHub repository in the project’s
   own authoritative `CONTROL.json`.
2. Retain v2.1 bidirectional `PROJECT_CONTEXT_ID` binding and add repository
   binding; never replace one with the other.
3. Make GitHub the durable source for the latest *synced* project state across
   GPT windows, without claiming that GitHub knows unpushed local work.
4. Let Codex perform local development, tests, and local commits during a
   temporary GitHub failure, returning a non-final local result.
5. Require commit, push, and remote verification before returning formal
   `PASS` for a GitHub-continuity Work Unit.
6. Preserve the existing controlled Git lifecycle, including parameterized
   direct-branch and PR-based workflows.
7. Fail closed for wrong repositories, stale state, unexpected remote heads,
   divergence, dirty worktrees, and unverified publication.
8. Keep credentials outside CONTROL, Instruction, Result, release packages,
   and all durable Framework state.

## Non-goals

- No production implementation in this design phase.
- No Kernel Contract change, Kernel rewrite, or new Kernel state.
- No breaking Schema change; `SCHEMA_VERSION` remains `1`.
- No global project registry, central database, daemon, vector memory, or
  conversation-memory store.
- No monorepo routing; v2.2.0 supports one project to one repository only.
- No forced use of pull requests, GitHub Actions, Codespaces, Packages, paid
  runners, Git LFS, or third-party state services.
- No automatic repository creation, remote replacement, history rewrite,
  force push, remote deletion, or unknown migration.
- No automatic migration of the Framework Management project as a prerequisite
  for building or releasing v2.2.0.

## Roles

### Developer

The Developer interacts with GPT and makes decisions that genuinely require
Owner/User approval. The Developer does not manually assemble project state or
splice Codex output into a new state record.

### GPT — PROJECT GOVERNANCE COORDINATOR

GPT selects or binds a GitHub repository through its supported access channel,
reads repository metadata and machine state, validates both project and
repository identity, resumes the latest verified synced state, determines the
next Work Unit, and generates a complete Paste-ready Codex Instruction. GPT
reviews the machine Result Envelope and decides the next governed action.

GPT does not implement local code, invent test results, use chat memory as
authority, or accept a foreign project result merely because its text looks
plausible.

### Codex — LOCAL EXECUTOR + REMOTE STATE PUBLISHER

Codex validates the local project and configured GitHub repository, performs
authorized local development and tests, updates state/evidence, commits,
pushes when authorized, verifies the remote result, and emits a Paste-ready
GPT Return derived from the machine Result Envelope.

Codex does not change project strategy, widen scope, replace GPT governance,
or push to a repository other than the bound repository.

### GitHub — PERSISTENT COLLABORATION LAYER

GitHub persists source code, Git history, canonical `CONTROL.json`, canonical
`STATE.json`, Work Units, Evidence, and machine Results that are included in
the selected branch/ref. GitHub is not the Framework Governance Engine, a
global registry, or an identity authority outside the project’s contract.

## Authority semantics

The authority model is deliberately split:

- `CONTROL.json` is the authoritative project configuration and repository
  binding.
- `STATE.json` is the authoritative current project state and revision. Its
  continuity section records observed sync facts; it does not create a second
  state machine.
- Work Unit, Evidence, and Result Envelope JSON are authoritative scoped
  machine records according to their existing contracts.
- Handoff text and Paste-ready GPT Return are derived views.
- GitHub is the durable cross-window source of the latest verified *synced*
  state, not a claim about every local checkout.
- A local Codex checkout may contain newer `LOCAL_UNSYNCED_STATE`. Only that
  local execution context can observe it until publication succeeds.
- README, issue text, PR description, commit message, or conversation memory
  may assist diagnosis but cannot override machine state or verified Git
  evidence.

Machine evidence from Git/GitHub is `TOOL_OBSERVED` or `SYSTEM_DERIVED`.
`MODEL_INFERRED` cannot establish repository identity, remote freshness, or
formal completion.

## Repository Binding

### Authoritative contract

The v2.2 additive binding is one top-level `github` object in the existing
authoritative `CONTROL.json`:

```json
{
  "github": {
    "repository_id": "123456789",
    "repository_full_name": "owner/project-a",
    "default_branch": "main"
  }
}
```

`repository_id` is the canonical decimal string representation of the stable
GitHub repository database ID and is the machine identity. It is never
replaced merely because the repository is renamed or transferred.

`repository_full_name` is the current human-readable/access name. It is
refreshed only through an explicit authorized migration when a rename or
transfer is observed. It is not the sole identity fact.

`default_branch` is the repository’s observed GitHub default branch. It is a
continuity hint and default target, not a command to push every project to
`main` or `master`.

`remote_name` is deliberately absent from durable `CONTROL.github`. It is a
local checkout fact, an instruction/preflight hint, or `TOOL_OBSERVED`
evidence. Codex enumerates local remotes and selects the uniquely matching
GitHub repository ID; a machine may call that remote `origin`, `github`, or
`upstream` without changing project identity.

A v2.2 GitHub-continuity project must contain exactly one valid binding. A
missing object is `GITHUB_REPOSITORY_UNBOUND`; malformed or conflicting data
is `GITHUB_REPOSITORY_MISMATCH` or `REPOSITORY_CONFLICT` as appropriate.

### Identity comparison

Codex obtains the actual repository ID from supported GitHub metadata/API or a
trusted authenticated CLI path, then resolves the configured remote. HTTPS
and SSH forms canonicalize to the same provider/repository target for
diagnosis, but a URL never outranks the observed repository ID.

The following are identity-safe:

- repository rename: same `repository_id`, updated full name, explicit
  migration of the human-readable field;
- repository transfer: same `repository_id`, updated full name, explicit
  migration;
- local directory move or rename: identity unchanged;
- HTTPS versus SSH remote: identity unchanged when provider and repository ID
  match.

The following fail closed:

- same project context with a different repository ID;
- same full name with a different repository ID;
- different project context with the same repository ID;
- an origin/selected remote resolving to a different repository;
- multiple remotes without an explicit local remote selection;
- an unbound, non-GitHub, or conflicting repository.

Repository path, folder name, Git remote URL spelling, repository full name,
commit message, and model inference cannot create or replace the binding.

## Multi-project isolation

Every executable instruction and authoritative return must satisfy both
identity layers:

```text
PROJECT_CONTEXT_ID  +  GITHUB_REPOSITORY_ID
```

The existing v2.1 context guardrail remains required. v2.2 adds
`github-repository-binding` as the repository safety guardrail for a project
adopting the continuity profile. No result or instruction is trusted merely
because one of the two identifiers matches.

The complete decision order is:

```text
instruction/result envelope
→ local/active PROJECT_CONTEXT_ID
→ configured repository binding
→ actual repository metadata and target remote
→ expected branch/ref and remote freshness
→ STATE revision
→ permission and Git authority
→ Work Unit authority
→ local execution
```

Any earlier mismatch stops later steps. In particular, a foreign repository
cannot update state, push, or return `PASS`.

The required isolation matrix is:

```text
Project A: PROJECT_CONTEXT_ID=A, REPOSITORY_ID=Repo-A
Project B: PROJECT_CONTEXT_ID=B, REPOSITORY_ID=Repo-B

GPT-A cannot treat Repo-B as the current project.
GPT-B cannot treat Repo-A as the current project.
Codex-A cannot push Repo-B.
Codex-B cannot push Repo-A.
A Result cannot drive GPT-B.
B Result cannot drive GPT-A.
same project + wrong repository → DENY
wrong project + same repository → DENY
```

The repository identity authority is specifically the stable
`CONTROL.github.repository_id`, not a local remote name, URL, path, or full
name.

## GPT → Codex Instruction binding

The v2.2 envelope is additive. Existing v2.1 fields remain and the following
fields are used for GitHub-continuity Work Units:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `target_project_context_id` | required for normal work | Existing project identity |
| `target_github_repository_id` | required for GitHub-continuity work | Stable machine repository identity |
| `target_github_repository_full_name` | optional diagnostic/access hint | Current human-readable name; never sole identity |
| `expected_state_revision` | required for mutating work | Existing optimistic state guard |
| `expected_base_sha` | required for Git-aware mutation | Local starting commit expected by GPT |
| `expected_remote_ref` | required when a remote target exists | Fully qualified target ref, such as `refs/heads/feature/x` |
| `expected_remote_head_sha` | required when remote is observable | Remote head GPT last verified |
| `expected_remote_name` | optional local execution hint | Preferred local remote name; cannot override repository ID |

`expected_remote_head_sha` may be null only for a read-only discovery,
repository bootstrap/migration, or explicitly offline local continuation. A
null value never authorizes a remote write without a fresh Codex preflight.

The builder must populate all fields from authoritative project state or
explicit GPT input. It must not infer a target repository from a chat title,
path, or project name. A normal instruction with a missing target project or
repository binding is rejected before the task body is interpreted.

## Codex → GPT Result binding

The Result Envelope remains the only machine Source of Truth. The Paste-ready
Return remains a derived view. Additive fields for required continuity results
are:

| Field | Meaning |
| --- | --- |
| `source_github_repository_id` | Bound repository machine identity |
| `source_github_repository_full_name` | Observed/current diagnostic name |
| `current_remote_ref` | Ref used for the continuity event |
| `local_head_sha` | Codex head observed at result creation/preflight boundary |
| `remote_head_sha` | Remote head observed by remote verification, timestamped by evidence |
| `sync_status` | `SYNCED`, `SYNC_PENDING`, or `RECONCILIATION_REQUIRED` |
| `push_status` | `NOT_ATTEMPTED`, `SUCCEEDED`, or `FAILED` |
| `remote_verification` | `NOT_ATTEMPTED`, `VERIFIED`, `UNAVAILABLE`, or `FAILED` plus observed evidence |

Existing `git.base_sha` and `git.implementation_sha` remain. A result may add
`git.publication_sha` and `git.commit_set` when the implementation and durable
publication require more than one commit. No second Return subsystem is
created.

For a required return, the renderer adds stable lines for repository identity,
remote ref/head, sync, push, and verification before the existing sections.
Missing fields render as `NONE`, preserving the v2.0.3 complete return
contract.

## Sync status and formal completion

The sync vocabulary is intentionally smaller than a new state machine:

- `SYNCED`: local publication was authorized; push succeeded; the target
  remote ref was independently verified; the result/evidence binding is
  valid.
- `SYNC_PENDING`: local development/tests/commit may be complete, but push or
  remote verification has not completed. Typical reasons are temporary
  GitHub outage, missing credentials, or an explicitly deferred publish.
- `RECONCILIATION_REQUIRED`: local and remote facts are stale, ahead in
  opposite directions, divergent, dirty, or otherwise unsafe to continue.

Result semantics are:

- `PASS` means `sync_status=SYNCED`, `push_status=SUCCEEDED`,
  `remote_verification=VERIFIED`, correct project/repository identity, current
  state revision, and no blocking deviation.
- `LOCAL_COMPLETE` is the explicit non-final result for successful local
  work with `sync_status=SYNC_PENDING`. It may be rendered as
  `RESULT: LOCAL_COMPLETE`; it is never a formal completion claim.
- `BLOCKED` or `FAIL` is used for policy, identity, verification, or test
  failure. A local test pass cannot upgrade a failed publish to `PASS`.

The existing Kernel state remains `VERIFYING`, `COMPLETE`, `BLOCKED`, or
`RECONCILIATION_REQUIRED`; `LOCAL_COMPLETE` is a Result Envelope outcome,
not a new Kernel state. A project may remain in `VERIFYING` with a pending
publication and must not advance to authoritative `COMPLETE` until the
existing revision/evidence rules and the continuity gate both pass.

## STATE continuity facts

The existing canonical `.gpt-codex/STATE.json` gains one additive object:

```json
{
  "continuity": {
    "current_remote_ref": "refs/heads/main",
    "latest_verified_remote_sha": "abc...",
    "latest_synced_state_revision": 12,
    "last_verified_result_ref": ".gpt-codex/evidence/results/RESULT-012.json",
    "sync_status": "SYNCED"
  }
}
```

These values are observed publication facts, not a second authority. The
ordinary local `revision` may be greater than
`latest_synced_state_revision` while `sync_status=SYNC_PENDING`; that is the
durable distinction between local and remote knowledge.

The stable resume entry is therefore the existing canonical files, not a new
pointer:

1. `.gpt-codex/CONTROL.json`
2. `.gpt-codex/STATE.json`
3. the Work Unit referenced by `STATE.active_work_unit`;
4. Evidence and the latest verified Result referenced by STATE/Work Unit;
5. GitHub metadata, the selected remote ref, and the verified remote SHA.

Handoff is regenerated from these records by the existing Handoff Skill. A
result file under the existing `.gpt-codex/evidence/` namespace is a durable
machine record, not a continuity index.

## GPT cross-window resume

The new GPT window must begin with an explicit repository selection/binding.
The resume gate is:

```text
USER SELECTS/BINDS PRIVATE REPOSITORY
→ GPT READS REPOSITORY METADATA AND REPOSITORY_ID
→ GPT READS CONTROL.json
→ validates PROJECT_CONTEXT_ID + GITHUB_REPOSITORY_ID
→ GPT READS STATE.json and continuity facts
→ resolves active Work Unit, Evidence, and verified Result
→ produces a resume summary from latest synced remote state
→ before mutation, asks Codex for local↔remote sync preflight
→ continue only if preflight is clean and bound
→ otherwise reconcile first
```

The resume summary must label `LATEST_SYNCED_REMOTE_STATE` separately from
`LOCAL_UNSYNCED_STATE`. GitHub cannot reveal unpushed commits or dirty files
on another computer. A resume based only on GitHub is therefore intentionally
limited to the latest verified synced state.

GPT must not infer current governance from README, issue, PR, commit message,
or old chat if machine state disagrees.

## Codex local/remote preflight

There are two deliberately different operation classes.

### NEW_WORK_PREFLIGHT

Before starting every new mutating Work Unit, Codex checks:

- local `PROJECT_CONTEXT_ID` and configured repository binding;
- actual repository ID and selected remote name/URL;
- current branch and fully qualified remote ref;
- dirty working tree and uncommitted files;
- local commits ahead of remote;
- remote commits ahead of local;
- local/remote divergence;
- expected base SHA;
- expected remote ref/head SHA;
- expected `STATE.revision`.

Outcomes are `CLEAN_SYNCED`, `LOCAL_AHEAD`, `REMOTE_AHEAD`, `DIVERGED`,
`DIRTY`, `IDENTITY_MISMATCH`, `UNBOUND`, or `REMOTE_UNAVAILABLE`. For
`NEW_WORK_PREFLIGHT`, only `CLEAN_SYNCED` permits starting a new mutating Work
Unit. Every other outcome denies new mutation and requires sync or
reconciliation first. No outcome triggers automatic overwrite, stash, reset,
rebase, merge, or force push.

### ACTIVE_WORK_DEGRADED_CONTINUATION

If the same Work Unit has already passed project/repository identity checks,
passed `NEW_WORK_PREFLIGHT=CLEAN_SYNCED`, received formal GPT authorization,
and is still active, a later temporary `REMOTE_UNAVAILABLE` does not
retroactively invalidate its local execution. That same Work Unit may continue
local editing, local tests, and explicitly allowed local commits. It may not
start another Work Unit, claim remote freshness, push without a successful
reconnect preflight, or return `PASS`. It must end as `LOCAL_COMPLETE` with
`SYNC_STATUS=SYNC_PENDING` unless it blocks for another reason.

When GitHub reconnects, Codex reruns identity validation and
`NEW_WORK_PREFLIGHT` for the active Work Unit. Unchanged remote state permits
publication; remote-ahead or divergence requires reconciliation before push.

## Git lifecycle integration

The v2.1 controlled Git lifecycle remains parameterized:

- `TASK_BRANCH` remains the default strategy where the project selects it;
- `EXISTING_BRANCH` and direct-branch development remain supported;
- PR-based integration remains supported but is not forced;
- `NO_COMMIT` remains available only when the project’s explicit policy allows
  it and cannot produce a continuity `PASS` without a publication contract.

v2.2 adds a continuity publication gate to the existing explicit Git
integration authority. It does not grant implicit push permission merely
because tests pass. A Work Unit that is expected to finish formally must
authorize the existing remote-write/integration capability in its scoped
permission contract.

The normal successful path is:

```text
LOCAL PREFLIGHT
→ IMPLEMENT
→ TEST
→ VERIFY
→ UPDATE STATE/EVIDENCE
→ COMMIT TASK-OWNED CHANGES
→ PUSH AUTHORIZED TARGET REF
→ VERIFY REMOTE REF/OBJECT
→ PUBLISH SYNCED RESULT
```

No branch name is hard-coded. For a PR workflow, the target is the authorized
feature ref and the Result can record the PR/ref as evidence; merge remains a
separate project-authorized integration decision. `PASS` requires the commit
that contains the governed execution result to be reachable from the verified
remote ref or an equivalent explicit remote evidence binding.

## Commit/state/result atomicity and bounded publication

Git cannot provide a distributed transaction between a local filesystem,
GitHub, and a self-referential Result file. v2.2 uses a finite two-commit
publication protocol:

1. `WORK COMMIT W` contains task-owned implementation, final logical code
   changes, the authorized state transition, and pre-publication evidence.
2. Codex pushes and verifies W when the selected workflow permits an early
   work publication. W is the implementation commit.
3. Codex creates `PUBLICATION COMMIT P`, containing the durable final Result
   Envelope, final continuity metadata, and references to W, the state
   revision, and the logical Work Unit result.
4. P must not contain `publication_sha=P`, `self_sha=P`, or any equivalent
   self-assertion. P may reference W and other already-known SHAs.
5. Codex pushes P and performs live `TOOL_OBSERVED` verification that the
   authorized target ref head equals P. That live observation, together with
   the persisted Result in P, is the completion evidence for the current
   execution. The Result need not contain P’s own SHA.

The durable semantic Result Envelope and live publication evidence are
distinct parts of the existing Evidence/Return model: the Result is the
authoritative semantic record, while the remote observation is
`TOOL_OBSERVED` evidence consumed by the current return renderer. No second
Result subsystem is created.

The protocol always terminates after at most W plus P, followed by observation;
there is no amend-and-republish loop. A missing W, missing P, local-only P,
failed push, or remote ref not equal to P produces `LOCAL_COMPLETE`,
`SYNC_PENDING`, `BLOCKED`, or `RECONCILIATION_REQUIRED`, never `PASS`.

Formal `PASS` requires these persisted facts:

- valid project and repository identity;
- W reference and valid state revision in the Result;
- durable Result Envelope and continuity metadata contained in P;
- no self-referential publication SHA;
- authorized target ref and commit-set references.

It also requires these live `TOOL_OBSERVED` facts after pushing P:

- the selected remote resolves to the bound `repository_id`;
- the authorized target ref is the observed remote ref;
- observed remote ref head equals P;
- P and W are reachable and the state/result files are present at P.

If live verification fails after P is pushed, the result is
`RESULT: LOCAL_COMPLETE`, `SYNC_STATUS: SYNC_PENDING`, and
`REMOTE_VERIFICATION: FAILED` (or `RECONCILIATION_REQUIRED` when the remote
advanced/diverged). It is recoverable by a later preflight and publication;
history rewrite and force push are forbidden.

### Publication answers

1. The implementation is contained in WORK COMMIT W.
2. The durable final Result is contained in PUBLICATION COMMIT P.
3. The durable Result may reference W, the state revision, the authorized
   target ref, the Work Unit, and already-observed remote evidence.
4. A commit must never write its own enclosing SHA; P must not contain P’s
   `publication_sha` or an equivalent self-reference.
5. Persisted PASS facts are valid dual identity, W reference, state revision,
   durable Result/continuity metadata in P, authorized ref, and valid commit-set
   references.
6. Live PASS facts are selected remote identity, target ref, remote head equal
   to P, reachability of W/P, and presence of the final state/result files at P.
7. A new GPT window independently re-observes GitHub’s repository ID and
   target ref/head, then reads P; it does not rely on old chat or P claiming
   that P was pushed.
8. Termination is guaranteed by the fixed sequence W → P → live observation;
   no amend-and-republish loop is permitted.
9. Partial publication is fail-closed: missing/local-only W or P, failed push,
   or an unexpected remote head yields non-PASS and a recoverable pending or
   reconciliation result.
10. A post-push remote verification failure returns
    `LOCAL_COMPLETE`/`SYNC_PENDING` with `REMOTE_VERIFICATION=FAILED`, or
    `RECONCILIATION_REQUIRED` when remote movement makes retry unsafe.

## Offline and GitHub failure behavior

When GitHub is unavailable before a new Work Unit begins,
`NEW_WORK_PREFLIGHT=REMOTE_UNAVAILABLE` denies the new mutation.

When GitHub becomes unavailable after the same Work Unit has passed identity
validation, `NEW_WORK_PREFLIGHT=CLEAN_SYNCED`, and GPT authorization, that
already-active Work Unit may continue local editing, local tests, and allowed
local commits. It may not start another Work Unit, claim remote freshness, or
return formal `PASS`. It must return:

```text
RESULT: LOCAL_COMPLETE
SYNC_STATUS: SYNC_PENDING
PUSH_STATUS: NOT_ATTEMPTED or FAILED
REMOTE_VERIFICATION: UNAVAILABLE or FAILED
```

The local state records the pending condition and does not overwrite the last
synced remote state. A new GPT window can recover only
`LATEST_SYNCED_REMOTE_STATE`; it cannot see or claim the local unsynced work.

When GitHub becomes available, Codex reruns identity and remote preflight. If
the remote is unchanged, publication may continue. If the remote advanced or
diverged, reconciliation is required before push. A successful bounded W/P
publication is a new event that may issue `PASS`; it is not a retroactive claim
that the earlier offline result was final.

## Failure and recovery codes

Stable machine reason codes are:

- `GITHUB_REPOSITORY_UNBOUND`
- `GITHUB_REPOSITORY_MISMATCH`
- `REMOTE_HEAD_MISMATCH`
- `LOCAL_REMOTE_DIVERGED`
- `SYNC_PENDING`
- `REMOTE_VERIFICATION_FAILED`
- `REMOTE_UNAVAILABLE`
- `DIRTY_WORKTREE_RECONCILIATION_REQUIRED`
- `STALE_STATE_REVISION`
- `EXPECTED_BASE_SHA_MISMATCH`
- `FOREIGN_PROJECT_CONTEXT`

Identity mismatch is checked before state mutation or Git write. Repository
binding migration, not runtime guessing, resolves unbound/conflicting states.
Dirty, ahead, behind, and divergence conditions use the existing Kernel
`RECONCILIATION_REQUIRED` state where appropriate. Recovery is explicit and
non-destructive: inspect, preserve, reconcile, then retry.

## Repository Binding Bootstrap and compatibility

The read-only compatibility scan classifies existing projects without changing
them:

- `ALREADY_BOUND`: exactly one valid GitHub binding and matching remote;
- `GITHUB_BINDING_REQUIRED`: Git repository exists but no binding is present;
- `LOCAL_GIT_ONLY`: Git exists but no remote is configured;
- `REMOTE_UNBOUND`: remote exists but cannot be safely identified as GitHub;
- `MULTIPLE_REMOTE_REVIEW_REQUIRED`: multiple possible remotes need explicit
  selection;
- `NON_GITHUB_REMOTE`: selected remote is not GitHub;
- `REPOSITORY_CONFLICT`: observed and configured identities disagree.

Migration is a separate authorized Work Unit. It may write the one `github`
object and a migration report after the user/GPT selects the exact repository.
It may not create a repository, replace or delete `origin`, force push, rewrite
history, or silently choose among multiple remotes. A local Git-only or
offline project remains usable locally but cannot claim a synced GitHub result
until binding and remote verification are complete.

The Framework Management project remains outside this bootstrap dependency.
After v2.2.0 capability and release verification, it should be migrated as a
separate ordinary governed project only if its owner explicitly chooses a
GitHub repository. Its management-only CONTROL identity must never be copied
into the release or into another project.

## Built-in model

The minimum reusable composition is:

1. retain `cross-project-context-binding` as the v2.1 required guardrail;
2. add a `github-repository-binding` Guardrail for fail-closed repository
   identity and push targeting;
3. add `github-project-continuity` as a Skill that implements the resume,
   preflight, publication, and offline result contract.

The new Guardrail belongs in the required safety catalog only for projects
adopting the v2.2 GitHub-continuity profile. The Skill is selected/enabled in
the project’s existing `CONTROL.extensions.skills[]` through the normal
versioned snapshot-copy process. It is not made a mandatory unrelated
Built-in for every project. `Preinstalled does not mean enabled` remains true.

## GPT and Codex access contracts

GPT may use an approved GitHub connector/app to read repository metadata, files,
commits, branches, PRs, and relevant status. Authentication is separate from
project identity: access to GitHub is not proof that the selected repository
is this project.

Codex uses local Git and already configured credential helpers or SSH
authentication. GitHub CLI/API use is optional capability detection, not a
paid-service dependency. The contract distinguishes:

- Git available;
- configured GitHub remote reachable;
- GitHub metadata/repository ID available;
- remote ref/object verification available.

Each capability can degrade to `SYNC_PENDING` or a migration/reconciliation
block with a precise reason. No token, PAT, connector credential, SSH private
key, or credential helper secret is written to project state, instruction,
result, evidence, or release package.

## Security and cost constraints

Private repositories are first-class supported targets. No public visibility
is required. Default operation needs only a GitHub repository and normal Git
operations. GitHub Actions, Codespaces, Packages, paid runners, Git LFS,
third-party databases, and hosted state services are optional and must not be
required by the continuity contract.

Release validation must scan source, templates, schemas, built-ins, scripts,
evidence, and generated packages for credentials. It must also ensure the
Framework Management project context does not leak outside its excluded local
CONTROL file.

| --- | --- | --- | --- |
| Source of Truth clarity | Highest; reuses existing authorities | Medium; pointer can be mistaken for authority | Medium; branch metadata adds another convention |
| GPT resume simplicity | Read existing known files and refs | One small entry file is convenient | Requires branch/tag discovery before state read |
| Git lifecycle compatibility | Highest; works with existing branch/PR policy | Good if pointer is updated transactionally | Lower; can conflict with project branch policy |
| Branch compatibility | Direct; state records current ref | Good but pointer can go stale per branch | Poorer for feature/PR branches and forks |
| Multi-project safety | Existing project + repo bindings apply directly | Pointer adds another routing surface | Tag/branch names are not identities |
| Offline handling | Explicit local vs synced facts in STATE | Pointer can hide pending local state | Separate branch can falsely look current |
| Implementation complexity | Small additive fields and shared checks | New file, generator, and repair rules | Branch/tag policy and lifecycle complexity |
| Migration cost | Add one binding and state continuity object | Add and populate pointer everywhere | Create/manage new refs and protections |

Approach B is acceptable only if future scale proves direct state discovery too
slow; it is not needed for v2.2. Approach C overfits a repository topology and
could pressure projects into a branch strategy. Approach A is recommended.

## Recommended architecture

Use **Canonical State Continuity with Repository Binding**:

- authoritative `CONTROL.github` binds one project to one GitHub repository;
- existing v2.1 context binding remains mandatory;
- additive `STATE.continuity` records the current remote ref, latest verified
  remote SHA, last synced revision, result reference, and sync status;
- the existing Result Envelope records repository identity, local/remote Git
  evidence, push, and verification outcomes;
- `github-repository-binding` enforces identity/push fail-closed behavior;
- `github-project-continuity` provides GPT resume, Codex preflight/publication,
  and local degradation;
- Handoff and Paste-ready Return remain derived views;
- no continuity pointer, registry, daemon, or second state system is added.

This is the smallest design that answers the cross-window resume question while
preserving v2.1 authority boundaries and the controlled Git lifecycle.

## Testing acceptance

The implementation plan must use TDD and cover at least these acceptance
groups:

### Repository identity

1. Same project/context and same repository ID allows, regardless of local
   remote name.
2. Same project and different repository ID denies.
3. Different project and same repository ID denies.
4. Different project and different repository ID denies.
5. Same full name with different repository ID denies.
6. Rename/transfer with stable repository ID passes after explicit name update.
7. Local directory move passes.
8. SSH and HTTPS canonicalize to the same bound repository.
9. `origin`, `github`, and `upstream` local names do not change identity.
10. A differing expected remote-name hint is diagnostic when repository ID
    uniquely matches.
11. Missing binding, multiple remote ambiguity, non-GitHub remote, and conflict
   produce migration/block outcomes without mutation.

### Freshness and Git safety

12. New Work Unit with remote unavailable is denied.
13. Authorized active Work Unit may continue locally after remote loss.
14. Degraded Work Unit cannot start a second Work Unit or return PASS.
15. Reconnect with unchanged remote permits publication.
16. Reconnect with remote-ahead/divergent state requires reconciliation.
17. Stale state revision and stale remote ref/head reconcile.
18. Dirty worktree, local-ahead, remote-ahead, and divergence are detected.
19. Expected base mismatch blocks.
20. Foreign repository cannot update state or push.
21. No force push, remote replacement, or destructive recovery is performed.

### Publication and result

22. Tests pass without push is not `PASS`.
23. Push plus remote SHA/ref verification is `PASS`/`SYNCED`.
24. Push exit success with observed SHA mismatch is not `PASS`.
25. GitHub unavailable after local completion is `LOCAL_COMPLETE`/
    `SYNC_PENDING`.
26. A later successful sync can produce a new `PASS`.
27. W/P publication terminates in bounded commits and never writes P’s own SHA.
28. Missing/local-only P and partial publication are detectable and recoverable.

### GPT resume and isolation

29. Correct repository independently verifies the remote ref/head for P before
    allowing resume.
30. Wrong repository blocks.
31. Missing binding requests migration.
32. Memory disagreement loses to machine state.
33. Projects A/B cannot exchange instructions, results, pushes, or resume state.

### Security, cost, and regression

34. Secrets are absent from CONTROL, Instruction, Result, Evidence, and ZIP.
35. Private-repository access works through separate authorization channels.
36. No GitHub Actions/Codespaces/paid service is required.
37. Git-only/local degradation tests work.
38. All 62 v2.1 tests and the v2.1 Context Binding, bootstrap, return,
    packaging, and Kernel tests remain passing.

## Kernel and Schema impact

`KERNEL_VERSION` remains `2.0.0`. The existing Kernel already defines
authority narrowing, evidence provenance, revision-guarded state writes,
reconciliation, and the rule that Git behavior belongs outside Kernel. v2.2
uses those contracts and adds no Kernel state or GitHub-specific rule to
`.gpt-codex/KERNEL.md`.

`SCHEMA_VERSION` remains `1`. Existing schemas use additive properties and
preserve v2.1 fields. The v2.2 implementation declares the new additive
properties and conditional required fields without invalidating v2.1 records.
If implementation discovers that either Kernel or Schema must change
breaking-compatibly, release work stops with
`KERNEL_CONTRACT_CHANGE_REQUIRED` or
`SCHEMA_BREAKING_CHANGE_REQUIRED`; this design does not authorize such a
change.

## Design self-review

- Cross-window resume: solved by selecting a repository, validating both IDs,
  then reading canonical CONTROL/STATE/result facts.
- Multi-project isolation: solved by retaining context binding and adding
  repository binding before interpretation or push.
- New Work Unit and already-active Work Unit offline semantics are separate;
  remote loss before start denies mutation, while remote loss after authorized
  start permits local degradation only.
- Publication is bounded to W plus P plus live observation; P never contains
  its own SHA and no infinite publication loop exists.
- Remote-name differences are local runtime facts, not project-global
  identity/configuration.
- GPT resume independently re-observes the selected remote ref/head before
  accepting publication state.
- GitHub omniscience: explicitly rejected; local unsynced state is labeled and
  not visible to a new GPT window.
- Second Source of Truth: none; STATE continuity is an additive fact section,
  Result remains authoritative, Handoff/Return remain derived.
- Controlled Git lifecycle: preserved; continuity uses explicit existing Git
  integration authority and remains compatible with direct/PR strategies.
- Paid GitHub features: not required.
- Credentials: none stored.
- v2.1 Context Binding: retained.
- Over-design: no pointer, registry, daemon, or new state machine.
- Kernel change: not required.
- Breaking Schema change: not required.
