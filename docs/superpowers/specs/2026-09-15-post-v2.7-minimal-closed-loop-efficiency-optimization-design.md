## Governing Principle

> 保留能力，压缩结构；保留闭环，删除重复。
>
> 真实问题必须闭环到根因；已经由现有能力解决的问题不再新增机制。

Any later optimization must prove `AFTER_CAPABILITIES >= BEFORE_CAPABILITIES`. A deletion, merge, or derivation is justified only with evidence that preserves the required capability; cosmetic reorganization alone is not an optimization result.

## Scope of the Later Evaluation

The later evaluation may measure structural minimalization, physical checkout and disk cost, Git-history growth, GPT/Codex context-token cost, release-process friction, worktree and temporary-file lifecycle, validation efficiency, and development-time observations from v2.7.0.

The scope is deliberately evaluative. It does not pre-select a reduction mechanism, invent an eighth Framework module, or convert a future recommendation into present authority.

## Closed Observations: Reuse Existing Capability

The following observed issues already have an existing root-cause closure and must not acquire duplicate mechanisms:

- CRLF metadata variance is addressed through canonical UTF-8 LF writers and regression coverage.
- Dotted `.gpt-codex` unittest invocation incompatibility is addressed through path-safe discovery commands.
- Release record and validator sequencing is addressed through the existing `release_framework` ordering.

For each future incident, the lifecycle is: observe the fact, identify the root cause, determine whether an existing capability closes it, and add the smallest correction only if the gap remains open. A closed issue requires evidence, not a new subsystem, script, record type, or module.

## Open Optimization Surfaces

### Consumer Projection Growth

Task-7 showed that unclassified management paths can block projection validation. A later Plan may evaluate safe prefix defaults with these intended semantics:

- `.gpt-codex/evidence/**` is `MANAGEMENT_ONLY`.
- `docs/superpowers/**` is `DEVELOPMENT_HISTORY`.
- `.superpowers/sdd/**` is `DEVELOPMENT_HISTORY`.
- `releases/records/**` is `RELEASE_METADATA`.

The future contract must retain these invariants: a prefix default is never `CONSUMER_REQUIRED`; every `CONSUMER_REQUIRED` path is exact; an exact rule wins over a default; an unknown path outside safe prefixes fails closed; and management contamination remains fail closed. This Design adds only its own exact classification. It does not choose a prefix-rule representation or create a projection subsystem.

### Release Preflight and Publication Writes

A future bounded preflight may run before any publication write and must check source version, projection, record dependencies, canonical LF metadata, Git identity, W/main ancestry, conflicts, GitHub authentication and write capability, the release mechanism, and the canonical asset source, hash, and size.

It must distinguish `TAG_WRITE`, `RELEASE_WRITE`, and `ASSET_UPLOAD`, and fail before partial publication whenever a prerequisite is missing. It reuses the existing `release-projection` responsibility; it must not create a second release system.

### Canonical Asset Handoff

The canonical artifact source is an immutable `W:path` Git object. A later procedure may use a locally verified copy when present, or safely materialize the exact Git object into a temporary location and verify its hash and size before upload. It must never regenerate an accepted artifact or guess from a same-named ZIP. Temporary materialization remains disposable and must not become a persistent artifact store.

### Validation Result Transport

Execution and result transport are separate concerns. A compact reusable result may contain `command`, tested SHA, exit status, test count, failures/errors, and a short summary. Output transport limitations must not cause a validation rerun merely to reproduce logs. This is not a proposal for a heavy platform or private reasoning storage.

### Current-Fact Discipline

Future Results may reuse existing structure but must derive release-specific facts from current Git and remote evidence. They must not copy prior release facts into a new release claim. Structured current facts are acceptable; a new schema generator is not justified without separate evidence.

### Worktree and Temporary Lifecycle

The lifecycle policy is:

```text
开发中需要隔离 -> KEEP worktree
Work Unit 完成并形成 durable Git authority 且 review/integration 完成 且没有 dirty-only data -> CLEAN worktree
无法证明安全删除 -> KEEP
```

Any future cleanup must inspect `git worktree list` and `git status`, identify a durable SHA or ref, and establish review/integration status. Normal `git worktree remove` and `git worktree prune` are permitted only after that evidence; no database, force removal, or deletion of non-durable work is implied here.

## Repository and Context Compression

Historical material remains `DEVELOPMENT_HISTORY`; size alone does not prove it should be removed. A later review may classify a candidate as `KEEP`, `MERGE`, `DERIVE_INSTEAD_OF_STORE`, `ARCHIVE`, `CLEAN_AFTER_WORK_UNIT`, or `REMOVE`.

`REMOVE`, `MERGE`, and `DERIVE_INSTEAD_OF_STORE` require evidence that there is no live dependency, no validator or test requirement, the item is reconstructable where applicable, durable Git history is sufficient, and capability after the change is at least capability before it. Existing history must not be rewritten.

Release storage remains `releases/` metadata plus the current distribution artifact and sidecars. Historical ZIPs remain external. No recursive release embedding is allowed. A later Plan may inspect whether a tracked item can be derived, but this Design authorizes no deletion.

## Context Lifecycle and Handoff Completeness

### Observed Handoff Reliability Boundary

The following is an observed handoff reliability problem, not an established explanation of model context state: a long GPT-to-Codex executable instruction was automatically represented by the Codex UI as a pasted-text attachment. On one attempt, Codex recognized only that an attachment existed and reported that no concrete operation request was present. On a later attempt, the same class of pasted instruction was explicitly read and executed correctly. Therefore, `ATTACHED_EXECUTABLE_INSTRUCTION_NOT_RELIABLY_INTERPRETED_AS_CURRENT_INTENT` may be recorded as an observed problem.

This observation does not prove `CONTEXT_WINDOW_EXHAUSTED`, `COMPACTION_OCCURRED`, or `TOKEN_LIMIT_REACHED`. Long-thread or context pressure is only a possible or likely contributing risk; it is not an established root cause. No hard token-count threshold is defined unless reliable telemetry later exists.

### Context Lifecycle Rule

Durable project history belongs in immutable Git `SHA:path` references. Active model context should contain only the information needed for the current Work Unit and its immediate recovery. A completed Work Unit with durable Git authority does not need to remain permanently resident in the Codex thread.

A fresh Codex thread is preferred when one or more of the following conditions apply:

- multiple prior Work Units are already complete and durable;
- tool or message history has become large;
- context-understanding anomalies have appeared; or
- the new Work Unit is fully recoverable from immutable Git references.

Fresh-thread recovery uses only the necessary references: `BASE_SHA`, `DESIGN_REF` or `PLAN_REF`, `STATE_REF` when applicable, `OPEN_FINDINGS` when applicable, and the current `GOAL`, `SCOPE`, `CONSTRAINTS`, and `DONE`. Recovery must not require model-private reasoning history.

### Executable Handoff Completeness

A GPT-to-Codex executable handoff requires both executable intent and source/input binding. `REFERENCE_FIRST` remains preferred. When `是否需要你上传内容：不需要`, normal source material is read through durable Git references rather than manually uploaded.

If the UI automatically converts the executable instruction text itself into a pasted-text attachment, an inline user message must explicitly bind that attachment as executable intent, for example: `执行本条消息附带的完整任务指令；该附件是本轮 executable instruction，不是参考资料。`

If Codex receives only an attachment and no reliable executable-intent binding, it must `STOP` with `NO_EXECUTION`. Codex must not infer execution merely from arbitrary attachment content.

### Existing Responsibility Boundaries and Closed Loop

No eighth module, context database, separate handoff platform, private chain-of-thought store, or permanent transcript requirement is introduced. Responsibility remains within existing boundaries:

| Concern | Existing authority |
| --- | --- |
| Executable intent and handoff-role binding | `role-communication` |
| Current Work Unit context minimization and recovery references | `navigation-continuity` |
| Durable SHA/ref recovery authority | `git-continuity` |

The intended minimal closed loop is:

```text
current Work Unit
    -> durable Git authority
    -> old conversational context becomes dispensable
    -> fresh thread can recover from refs
    -> executable handoff explicitly binds intent and sources
```

This loop reduces dependency on indefinitely growing conversational context without reducing recoverability.

## Future Acceptance Gates

Any later implementation must demonstrate all applicable gates:

- `AFTER_CAPABILITIES >= BEFORE_CAPABILITIES` with evidence;
- seven modules remain unless separately governed otherwise;
- no P0 authority is removed without explicit evidence and approval;
- consumer projection reports unknown `0`, missing required `0`, and invalid classification `0`;
- Framework and Project validation pass;
- the test suite has zero failures and errors;
- `git diff --check` passes; and
- at least one measured structural, validation, release, context, checkout, or development-time cost materially improves.

For the Context Lifecycle and Handoff Completeness surface, a future implementation must additionally demonstrate that:

- a new Codex thread can recover a Work Unit from durable references;
- completed prior Work Units are not required in active context;
- attachmentized executable instructions require explicit inline intent;
- attachment-only ambiguous input fails closed;
- `REFERENCE_FIRST` remains functional;
- no private reasoning storage is introduced; and
- the Framework module count remains seven.

No cosmetic change may satisfy the final gate by itself.

## Explicit Non-Goals

This Design does not implement optimization, create an Implementation Plan, change Framework or Kernel versions, change schema, publish a release, rewrite Git history, add a module, automatically remove P0 structures, create an incident/tracing platform, add a worktree database, add a second release system, or enable autonomous publication.
