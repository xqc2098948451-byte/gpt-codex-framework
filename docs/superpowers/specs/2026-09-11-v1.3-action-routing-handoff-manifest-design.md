# GPT–Codex Framework v1.3 — Action Routing & Handoff Manifest Design

## Goal

Remove ambiguity about where GPT-issued instructions must be executed and remove guesswork about which artifacts the user must provide to GPT at task boundaries or when switching GPT windows.

## Scope

This is a universal governance upgrade. It does not redesign any project business architecture, task content, implementation stack, or domain model.

## Action Routing Protocol

Every actionable step emitted by GPT must identify exactly one route:

- `USER_LOCAL` — the user performs the action in their local environment.
- `CODEX` — the user copies the bounded instruction block to Codex.
- `RETURN_TO_GPT` — the user returns the named result/artifacts to GPT.
- `INFO` — explanatory material; no action is required.

Unlabeled prose must not be interpreted as an executable instruction. Codex copy blocks must use explicit START/END boundaries. GPT should minimize `USER_LOCAL` work when Codex can safely perform the operation under an approved mode.

Dependent multi-step flows must stop at decision boundaries rather than giving the user future actions that depend on unavailable results.

## Handoff Manifest Protocol

Add `.gpt-codex/HANDOFF.md` as a derived current handoff manifest. It answers what must be delivered to GPT next; it is not an authority source.

`HANDOFF.md` contains:

- handoff type and current lifecycle/task binding;
- state/head binding used to detect staleness;
- `REQUIRED_FILES`;
- `REQUIRED_RESULT`;
- `OPTIONAL_FILES` with reasons;
- `DO_NOT_SEND_BY_DEFAULT`;
- `NEXT_GPT_ACTION`;
- manifest freshness status.

The policy is Minimum Handoff First / Evidence On Demand. The user should not need to infer which files are relevant.

## Authority and Freshness

`PROJECT.md` defines what the project is. `STATE.md` describes where it is. `HANDOFF.md` derives from those and points to what GPT needs next.

If `HANDOFF.md` conflicts with higher-authority artifacts, the manifest is stale. Return or record `HANDOFF_STALE`, regenerate it from authoritative state, and do not use the stale manifest as evidence.

Codex may update `HANDOFF.md` only when the active mode explicitly authorizes the mechanical handoff refresh. Such a refresh cannot grant implementation permission, approve tasks, alter architecture, or change repository validation.

## Integration

Update Framework, Bootstrap Prompt, AGENTS, README, Project/State/Task/Execution/Discovery/Governance/Review templates, and Changelog. Add `HANDOFF.template.md` and `ACTION_ROUTING.template.md`.

Compact Codex returns should include `HANDOFF_REF: .gpt-codex/HANDOFF.md` when a next GPT handoff exists.

## Success Criteria

1. No framework path requires the user to guess whether an instruction is local or for Codex.
2. No normal handoff requires the user to infer which project files GPT needs.
3. New GPT windows can resume by following the current manifest and durable state.
4. A stale manifest is detectable and cannot override project/state/task/Git facts.
5. Existing Bootstrap Validation, Compact Handoff, Context Continuity, Task/ADR/Review/Lesson behavior remains intact.
