# v2.2.1 Consumer Projection Release Boundary Design

**Status:** Design-only work unit; implementation and GitHub publication are not authorized by this work unit.

**Target:** `xqc2098948451-byte/gpt-codex-framework`, `refs/heads/main`

**Baseline:** remote `954221c75aca086a901294e26207e3ddd5c189a7`, Framework `2.2.1`, Kernel `2.0.0`, Schema `1`

## Decision

Adopt **Approach 2: Management Repository plus Consumer Projection**.

GitHub `main` remains the complete authoritative Framework Management Repository. The bootstrap ZIP is a separately validated consumer-safe release projection generated from an explicit positive inventory. A repository checkout is therefore not a consumer package, and no consumer may copy the repository root as its Framework source.

This work unit only defines the boundary. It does not change `VERSION`, production release code, validators, schemas, templates, Built-ins, tests, management state, evidence, results, release metadata, artifacts, commits, or GitHub.

## Logical Surfaces

### `MANAGEMENT_REPOSITORY_SURFACE`

The complete repository on `main` may contain:

- generic Framework source, Kernel, Built-ins, schemas, templates, and tests;
- management-only scripts, self-hosting tests, and extensions;
- `CONTROL.json`, `STATE.json`, Evidence, and Result records;
- `docs/superpowers/specs/**` and `docs/superpowers/plans/**`;
- `releases/INDEX.json` and `releases/records/**`;
- current generated `dist/` artifacts;
- legitimate development and audit history.

This surface is the Framework Management project's authoritative source and history. Its legal presence of a real management identity must not make the complete-repository Framework Validator fail.

### `CONSUMER_PROJECTION_SURFACE`

The consumer surface is a generated staging tree containing only files explicitly classified `CONSUMER_REQUIRED`. The deterministic ZIP is built from that staging tree, with one versioned top-level directory. The projection is a release projection, not a repository clone snapshot.

The projection must exclude management configuration and state, Evidence/Result, the real management context and GitHub identity, management-only migration records, development/audit history, local Git metadata, caches, temporary files, old release ZIPs, and secrets. `docs/superpowers/specs/**` and `docs/superpowers/plans/**` are always management history and never consumer inputs.

### `RELEASE_HISTORY_SURFACE`

The Management Repository retains `CHANGELOG`, `releases/INDEX.json`, `releases/records/**`, design/plan history, and historical governance evidence required for audit continuity. These are not automatically consumer files. Release metadata is used by publication validation and sidecar verification; only a path explicitly classified `CONSUMER_REQUIRED` may enter the ZIP.

## Positive Projection Model

The release pipeline will use a small JSON manifest at:

```text
.gpt-codex/release/consumer-projection-manifest.json
```

The manifest is management release metadata and is itself excluded from the projection. It has `manifest_version`, `framework_version`, `projection`, and a `paths` object whose keys are exact POSIX file paths and whose values are one of:

- `CONSUMER_REQUIRED`
- `MANAGEMENT_ONLY`
- `DEVELOPMENT_HISTORY`
- `RELEASE_METADATA`
- `GENERATED_ARTIFACT`
- `LOCAL_ONLY`

The manifest is intentionally an exact file inventory, not a glob policy or a new policy language. A path may have only one classification. The projection builder selects only exact `CONSUMER_REQUIRED` entries. A new non-local path absent from the manifest is `UNKNOWN/UNCLASSIFIED`: it is excluded from staging and causes release validation to fail. A required manifest path missing from the source also causes release validation to fail. This makes future Management-only additions opt-in rather than silently packageable.

The audit may use a fixed implementation-level skip set for `.git`, Python caches, test caches, editor metadata, and temporary staging roots. Those are operational `LOCAL_ONLY` inputs and never become projection entries; every other source or generated path must be explicitly classified.

## Classification and Inventory Audit

The implementation must mechanically enumerate the current v2.2.1 source tree before finalizing the manifest. The audit must report every path, its classification, its inclusion decision, and a reason. It must not infer inclusion merely from directory ownership.

The following principles govern the audit:

| Classification | Rule | Default projection decision |
| --- | --- | --- |
| `CONSUMER_REQUIRED` | Needed to bootstrap, validate, or reuse a consumer Framework workspace at runtime; contains no real Management identity. | Include |
| `MANAGEMENT_ONLY` | Management `CONTROL`/`STATE`, Evidence/Result, self-hosting/publication authority, or a test/tool whose contract is specifically this Management project. | Exclude |
| `DEVELOPMENT_HISTORY` | Design, Plan, historical roadmap, audit narrative, or other development history not needed for consumer bootstrap. | Exclude |
| `RELEASE_METADATA` | Release index/records and publication bookkeeping used to identify or verify an artifact rather than bootstrap a consumer workspace. | Exclude unless the audit proves a specific file is a consumer requirement |
| `GENERATED_ARTIFACT` | Current ZIP, sidecar, release JSON, or other generated output. | Exclude from the ZIP; publish beside it as release output |
| `LOCAL_ONLY` | Git metadata, caches, temporary files, editor debris, or staging output. | Exclude |

The audit must explicitly review these current groups: `AGENTS.md`; `.gpt-codex/README.md`; `.gpt-codex/BOOTSTRAP_PROMPT.md`; `.gpt-codex/KERNEL.md`; `.gpt-codex/schemas/**`; `.gpt-codex/project-template/**`; `.gpt-codex/builtins/**`; `.gpt-codex/scripts/**`; `.gpt-codex/extensions/skills/framework-release/**`; `.gpt-codex/MIGRATION_*.md`; `.gpt-codex/CHANGELOG.md`; `VERSION`; `releases/**`; `.gpt-codex/tests/**`; `tests/**` if present; `docs/superpowers/**`; and `dist/**`.

The expected audit direction is that core bootstrap instructions, Kernel, schemas, templates, Built-ins, and only the generic scripts/extensions actually required by bootstrap are candidates for `CONSUMER_REQUIRED`. Management release tooling, publication authority, self-hosting tests, management continuity tests, `framework-release`, release history, design/plan history, and generated artifacts remain excluded unless the audit produces evidence that a particular file is required by a consumer. The final manifest, not this design's candidate list, is the authority.

## Tests and Synthetic Fixtures

Tests are classified individually. The implementation must distinguish:

1. consumer/bootstrap validation tests that add consumer value;
2. generic Framework development regression tests; and
3. Management-only/self-hosting/publication tests.

Management-specific tests, including the current `test_local_corrective_state.py` that asserts the real Management identity, remain in the Management Repository and are excluded from the projection. A generic test or fixture that genuinely belongs in a consumer package may enter only after it is rewritten to use synthetic UUIDs, synthetic repository IDs, and synthetic project names. The real context `cb1e0450-df32-4ff6-8a33-35187b69a866`, repository ID `1366213495`, repository name `xqc2098948451-byte/gpt-codex-framework`, and Management project identity may never appear in consumer projection bytes.

The projection validator scans the staging tree and the final ZIP, not the complete Management Repository. It must reject the real Management context, repository ID/full name, project ID/name, exact management file paths `.gpt-codex/CONTROL.json` and `.gpt-codex/STATE.json`, Management Evidence/Result paths, credential material, and secret-like content. Generic documentation may mention the words `CONTROL.json` or `STATE.json`; those mentions are not contamination. Historical Management IDs are legal in the Management Repository and historical design/plan files, so those files are boundary exclusions rather than reasons to reject the repository as a whole.

## Release Pipeline and Integrity Semantics

The existing release pipeline remains the orchestrator. Its minimal change is:

```text
validate complete Management source
  -> audit exact manifest and fail on unknown/missing paths
  -> create temporary consumer projection staging root
  -> copy only CONSUMER_REQUIRED files
  -> validate staging boundary and contamination
  -> create deterministic ZIP from staging root
  -> compare staging inventory and ZIP inventory byte-for-byte
  -> write sidecar SHA and release JSON
```

The temporary staging root is outside the source inventory and is removed after packaging. The ZIP must not be built directly by walking the Management Repository.

The old incorrect invariant is retired:

```text
GENERIC_REPOSITORY_TREE == RELEASE_ZIP_TREE
```

The replacement invariants are:

```text
CONSUMER_PROJECTION_TREE == RELEASE_ZIP_TREE
CONSUMER_PROJECTION_RELEASE_MATCH = PASS
MANAGEMENT_REPOSITORY_CONSUMER_BOUNDARY = PASS
```

The first invariant proves that the artifact exactly represents its generated projection. The second proves the projection is safe and complete. The third proves the full Management Repository remains internally valid while its management surface stays outside the consumer package.

## Alternatives Considered

### A. Blacklist-based exclusions

This is the smallest apparent edit to the current `collect_files` walk, but it is unsafe as the repository grows: every newly added Management-only path is included until someone remembers to extend the blacklist. It also makes contamination prevention depend on an ever-growing negative list. Rejected as the primary model.

### B. Positive allowlist plus temporary staging (chosen)

An exact manifest makes inclusion explicit, gives unknown paths a safe fail-closed behavior, and can reuse the existing deterministic ZIP writer after staging. The temporary tree gives the release validator a concrete boundary to scan and makes byte-for-byte ZIP comparison straightforward. This is the smallest design that satisfies the safety requirement without changing the Kernel, Schema, or adding a service.

### C. Separate permanently generated consumer tree

A checked-in or long-lived generated tree would make the boundary visible, but it introduces synchronization, stale-generated-source, and review noise. A temporary generated staging tree provides the same validation boundary without creating another source of truth. Rejected unless implementation discovers a concrete limitation in the existing pipeline.

## Acceptance Criteria for the Future Implementation

- The complete Management Repository may contain the real Management identity and still pass its Framework Validator.
- The exact consumer manifest is complete; unknown non-local paths fail release validation and missing required paths fail release validation.
- Consumer projection and ZIP inventories match exactly and deterministically.
- The consumer projection contains no real Management identity, management files, history, caches, secrets, or old release ZIPs.
- Historical design/plan files are unchanged.
- v2.2.0 artifact metadata and SHA are unchanged.
- The new v2.2.1 artifact has a new SHA, and all current v2.2.1 metadata points to it.
- Existing 114 tests remain passing, with new projection tests also passing.
- Kernel remains `2.0.0`; Schema remains `1`; no breaking contract is introduced.
- W/P attestation and confirmed-baseline-only GitHub publication rules remain intact.
