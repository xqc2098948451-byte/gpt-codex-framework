# Migration Guide — v1.7 to v2.0

v2.0 is not a mechanical rename of v1.7. It is a structural reduction.

## Do not bulk-copy v1.7 governance

Do not copy `FRAMEWORK.md` or every v1.x capability artifact into the new project merely to preserve behavior. First discover what the actual project still needs.

## Concept mapping

| v1.7 concept | v2.0 treatment |
|---|---|
| `PROJECT.md` | remains human project intent/architecture |
| `STATE.md` | becomes machine-authoritative `STATE.json` (optional human views are derived) |
| `HANDOFF.md` | derived view generated by Handoff Built-in |
| Task / Feature | represented by generic Work Unit; richer semantics may be project Skill |
| Git protocol | Built-in/project Skill + Guardrails, not Kernel |
| Parallel protocol | project/optional Skill, not Kernel |
| Observability | project/optional Skill + Fitness, not Kernel |
| Specification workflow | project/optional Skill, not Kernel |
| Golden Principles | project Guardrails/Fitness when machine-checkable; human principles otherwise |
| Hygiene | project/optional Skill, not Kernel |
| Reconciliation-specific states | one Kernel `RECONCILIATION_REQUIRED` + source/reason |

## Migration sequence

1. Keep the existing v1.7 project untouched.
2. Place v2.0 framework beside it as framework root.
3. Run read-only project discovery.
4. Generate a v2.0 Reuse Report from actual project needs.
5. Create `PROJECT.md`, `CONTROL.json`, `STATE.json` in a migration branch/workspace.
6. Map only actively needed v1.7 capabilities to Built-ins or project-local extensions.
7. Validate governance and behavior.
8. Obtain explicit approval for material migration changes.
9. Adopt v2.0 only after migration verification; do not infer adoption from compatibility evaluation alone.

## History

Framework development history remains in this distribution under `docs/superpowers/`. Business projects may choose separately whether they keep framework-development history locally.
